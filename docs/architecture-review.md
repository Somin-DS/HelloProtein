# HelloProtein 아키텍처 검토

2026-09-23. 본사 개발자 역할(`/Users/somin/personal/shared-personas/developer.yaml`)과 기존 개발자 보고서를 읽고, Android 출시·날짜별 편집 요구를 반영해 소스를 다시 검토했다. 정적 검토이며 이번에 코드 변경·빌드·앱 실행은 하지 않았다.

## 판단

전반적인 구조 개선이 필요하다. 이유는 UIKit이나 코드 연식이 아니라 **화면 표시와 데이터 변경이 결합돼 있고, 날짜별 기록이라는 핵심 모델이 없기 때문**이다. 현재 구조에 과거 편집·AI·결제를 계속 붙이면 같은 데이터 불일치 문제가 확장된다.

다만 모든 UIKit 화면을 먼저 MVVM으로 옮기는 대규모 정리도 권하지 않는다. Android 요구가 추가됐으므로 기존 사용자 데이터 읽기 경계는 보존하고, 공통 기술을 작은 구현으로 검증한 뒤 선택한 구조에서 기능 단위로 교체해야 한다. Flutter 확정이나 전면 재작성 승인은 아직 아니다.

## 적정 목표 구조

```text
화면 + 화면 상태
       ↓
기록 추가/수정/삭제 · 날짜 조회 · 통계 계산
       ↓
기록 저장소 / 식품 검색 / 설정 경계
       ↓
로컬 DB · 외부 API · 플랫폼 기능

iOS 기존 Realm/UserDefaults → 별도 이관 경계 → 새 저장소
```

- 화면은 DB 객체를 직접 쓰지 않고 저장 결과와 오류를 받아 표시한다.
- 핵심 기록 모델에는 안정적 ID, 해당 달력 날짜, 단백질량, 선택적 음식명/수량/단위/출처를 둔다. 시각과 날짜 귀속 정책은 함께 결정한다.
- 기존 합계만 있는 날짜는 상세 기록을 지어내지 않고 별도로 보존한다. 그 날짜에 추가·수정할 때 보정/합산 규칙을 명시한다.
- 목표·검색 언어와 기록 저장은 역할을 분리한다. 앱의 모든 기능에 형식적인 UseCase/Repository 클래스를 하나씩 만들 필요는 없다.
- AI와 구독은 기록 저장의 필수 의존성이 되지 않도록 독립 경계로 추가한다. 실패해도 수동 기록은 작동해야 한다.

## 신규 MigrationCore 평가

유지할 가치가 있다. `MigrationCore/Sources/MigrationCore/LegacyMigration.swift:84`는 외부 저장소 없이 변환하고, 합계 차이 보존·중복 거부·정수 범위 검사로 기존 코드보다 명확한 책임을 가진다. 그러나 이관 완료 코드가 아니라 **변환 규칙의 첫 초안**이다.

실제 연결 전에 필요한 보완:

1. `LegacySnapshot`은 SearchHistory, 원본 Date와 원본 현재 날짜 문자열을 포함하지 않는다(:5). 원본 백업/추출 증거 형식과 정규화 전 데이터 보존을 별도로 설계해야 한다. 날짜 모호성을 변환 전 단계에서 소실시키지 않는다.
2. 중복 날짜/현재 날짜 충돌 시 전체 변환이 실패한다(:97). 임의 합산하지 않는 건 옳지만, 실패 후 앱이 기록을 잃은 것처럼 보이지 않는 복구 화면·진단·재시도 상태가 필요하다. 예외만으로 출시할 수 없다.
3. 안정적 ID로 정렬하고 동일 계획을 만드는 것은 DB 재실행 안전성과 다르다(:55). 실제 import 상태, 원자적 쓰기, 검산, 완료 마커, 중단 복구를 구현하고 검증해야 한다. 나중에 다시 이관할 때 사용자의 새 수정값을 이전 원본으로 덮어쓰지 않도록 한다.
4. `currentFoods`와 `favorites`를 ID로 정렬한다(:126, :130). 기존 Realm 목록의 사용자에게 보이던 순서가 의미 있다면 순서 필드를 보존해야 한다. 결정적인 출력과 표시 순서 보존을 혼동하지 않는다.
5. `MigrationPlan`은 Codable 자동 디코딩으로 검증을 우회해 생성 가능하다(:57). 이후 JSON을 실제 입력 경계로 쓰면 schemaVersion·날짜·ID·합계를 import 시 재검증한다. Swift 타입만으로 다른 런타임과 숫자 범위가 같아지는 것은 아니다.
6. 원본 음수값을 보존하는 것과 새 입력에서 음수를 허용하는 것은 구분한다. MigrationCore의 Int 레거시 형식을 미래 소수 입력용 도메인 모델로 그대로 쓰지 않는다.
7. `currentDay`는 실행 시점의 오늘이 아니라 구버전이 마지막으로 저장한 날짜다. 이름/계약을 명확히 하고 미래 도메인 모델을 `LegacySnapshot.Food`와 분리한다. 며칠 뒤 앱을 여는 경우 기존 상세를 오늘로 이동시키지 않아야 한다.

실행 문서의 11개 테스트는 순수 변환 테스트다. 실제 구버전 Realm 읽기, 새 저장소 쓰기, 자정/시간대, 앱 종료 후 재개, UI는 아직 통과 증거가 없다.

기존 `SceneDelegate.swift:30`과 `:40`의 활성화/포그라운드 처리는 비어 있다. 날짜 전환이 `ShowViewController.viewWillAppear`에만 있어 화면을 유지한 채 자정을 넘기는 경우의 처리도 검증 대상이다. 새 날짜 선택 상태와 날짜 계산은 화면 재등장 여부에 의존하지 않도록 한다.

## 작업 순서

1. 재현 가능한 기존 빌드·배포 소스 매핑·저장 키/형식 목록을 확보한다. 설정 비밀값과 지원 OS 결정을 구분한다.
2. 기록/달력 날짜/합계/레거시 보정 규칙과 저장소 인터페이스를 결정한다. 원본 읽기와 비파괴 백업 경계를 먼저 검증한다.
3. Android를 포함하는 기술 검증을 한다. 후보 하나로 양쪽 플랫폼의 날짜별 추가·편집, iOS 원본 읽기→새 저장소 연결을 짧게 완주한다. 결과로 공통 UI 재구축 또는 네이티브 유지 범위를 확정한다.
4. 실제 이관과 복구를 구현한다. 기존 사용자 데이터 보존이 통과해야 UI 전환을 배포한다.
5. 기록 화면→검색/즐겨찾기→통계/설정 순으로 기능 단위를 새 구조에 연결한다. 영어 검색/입력 값 검증을 해당 단위에서 함께 해결한다.
6. 안정화 후 AI 체험과 구독을 추가한다.

결론적으로 **리팩토링은 업데이트의 첫 설계 작업에 포함해야 한다.** 현재 코드 전체를 먼저 미적으로 정리하는 별도 프로젝트보다, 데이터 보존과 Android를 기준으로 경계를 확정하고 실제 기능을 옮기는 작업이 유효하다.
