## 목적과 기준

기존 사용자의 즐겨찾기와 검색 기능을 새 SwiftUI 흐름에 연결한다. 반복 기록을 쉽게 하되 이관된 원문·날짜별 기록·저장 결과 미확정 계약을 보존한다. [PR #7](https://github.com/Somin-DS/HelloProtein/pull/7) 병합 커밋 `c4ab6442c8d97f92d33a5c0768255b1a5c0686f0` 이후 최신 main을 구현 기준으로 삼는다. 이번 계획 작성 당시 로컬은 수정 커밋 `582bd55`다. 무관한 사용자 파일을 삭제하거나 일괄 stage하지 않는다.

본사 7개 직무의 의견과 조정 결과는 [공동 검토 기록](reviews/2026-10-07-favorites-search-team-review.md)에 남긴다. 현재 계획은 저장소 코드와 기존 문서 검토에 근거한다. Figma 재열람·외부 API의 현재 가용성·단위·이용 조건은 이번에 확인하지 않았다.

A에 동작하지 않는 검색 탭을 미리 보여주지 않는다. B는 공급자 데이터의 기준량·출처·현재 API 계약 확인이 선행 조건이다. 확인되지 않은 공급자는 직접 추가를 활성화하지 않으며, A 진행을 그 조사 때문에 막지 않는다. B의 일부만 구현하고 검색 복원 전체 완료라고 보고하지 않는다.

기존 무료 즐겨찾기에 개수 제한·구독 잠금을 추가하지 않는다. Android·Duo·새 분석 SDK·온보딩·최소 OS·새 흐름 기본 활성화·출시는 두 PR 모두 제외한다.

## 확인한 현재 상태

- `AppState.favorites`는 `FavoriteFood(id, name, proteinCentigrams, position, legacySourceID)`다. 이름과 signed 단백질량을 이관 원문대로 보존하며 생성자 자체는 양수 검증을 하지 않는다.
- `AppState.searchHistory`는 `SearchTerm(id, value, position, legacySourceID)`다. 검색 시각이나 언어 필드는 없다. 이관 순서를 실제 시간순으로 추정하지 않는다.
- `AppState.validate`는 즐겨찾기와 검색어 각각의 ID·position 중복을 거부한다. 배열 순서와 position을 모두 일관되게 관리해야 한다.
- 검색 언어는 이미 `state.settings.searchLanguage`로 이관된다. 새 UI에서 구 UserDefaults를 다시 읽거나 쓰지 않는다.
- 기존 UIKit 검색은 영어에서 키워드를 무시하고 전체 파일을 반환한다. 한국어는 URL에 검색어를 직접 삽입하고, 여러 실패 경로에서 로딩 종료·오류 안내가 빠진다. 이 코드의 동작을 그대로 복사하지 않는다.
- `Protein-En.json`은 2,332개 행의 `Food`·`Protein` 값만 갖는다. 기준량·출처·식품 ID가 없다. 기존 문자열의 ‘100g 기준’만으로 실제 데이터 단위를 검증했다고 볼 수 없다.
- 기존 `Food` 모델도 한국어 `DESC_KOR`·`NUTR_CONT3` 위주이며 기준량을 표현하지 않는다. 새 검색 결과 모델은 UI와 공급자별 응답 모델을 분리한다.

## A: 추가 시트와 초안 정책

현재 홈의 단일 추가 버튼을 유지하고, 열 때의 선택 날짜를 세션 `targetDay`로 고정한다. 오늘·과거 모두 기록할 수 있다. **목표 화면과 달리 자정 이후에도 이 날짜를 유지**하며 오늘 날짜로 강제 갱신하지 않는다. 기존 기록 수정 시트와 하루 총량 시트는 탭형 추가 시트로 바꾸지 않는다.

A는 직접 입력/즐겨찾기, B는 직접 입력/검색/즐겨찾기 탭을 제공한다. 일반 iPhone의 작은 폭·AX3에서 탭 제목을 읽고 선택할 수 있게 하고 선택 상태를 접근성에 전달한다.

### 탭 전환 정책 — 한 번에 한 작업

숨은 탭 초안을 저장 성공 때 잃는 일을 피하기 위해 **탭 전환 시 현재 입력·선택을 버릴지 확인**하는 방식으로 확정한다.

- 현재 직접 입력 값이나 ‘즐겨찾기에도 저장’ 선택이 초기 상태와 다르거나, 검색/즐겨찾기에서 선택한 음식이 있으면 전환 확인을 표시한다.
- 머무르기는 탭·입력·선택·ID 유지. 버리고 이동은 현재 초안·선택만 지우고 목적 탭으로 이동한다. 확인 전 탭은 바뀌지 않는다.
- 단순 검색어·검색 결과·이력 펼침만으로 버리기 확인을 띄우지 않는다. 검색과 즐겨찾기 선택을 섞는 장바구니는 이번 범위가 아니다.
- busy/pending에는 탭 이동·새 쓰기·입력 변경을 막는다. 닫기는 Phase 1B 정책을 따른다.
- 기존 기록 수정 중 ‘즐겨찾기에도 저장’ 선택은 그 수정 초안의 일부다. 다른 즐겨찾기를 삭제하는 별 해제 동작으로 해석하지 않는다.

직접 입력은 상단 저장, 목록은 하단 ‘N개 추가’와 단백질 합계·대상 날짜를 사용한다. 선택 0개이면 추가 비활성. 목록의 기록 추가 선택 영역과 편집·삭제 버튼은 각각 최소 44pt의 독립 터치 영역 및 구분되는 접근성 label을 제공한다. 입력/선택 전체 버리기·삭제·오류·탭 전환 확인은 하나의 표시 정책으로 직렬화한다.

## A: 즐겨찾기 데이터와 관리

### 조회·선택

목록은 `position` 오름차순으로 표시한다. 기존 ID·이름·값·legacySourceID는 조회만으로 변경하지 않는다. 공백/빈 이름은 표시용 ‘이름 없음’으로 보이되 저장 원문을 덮어쓰지 않는다. 양수인 빈 이름 즐겨찾기는 FoodRecord의 이름 없음으로 기록할 수 있다.

0·음수·양수 변환 불가능한 값은 목록에서 숨기지 않는다. 저장된 signed 값을 그대로 표시하고 기록 추가 선택만 차단한다. ‘단백질량을 확인해 주세요’ 안내와 **실제 즐겨찾기 편집 경로**를 제공한다. 자동 절대값·0 clamp·자동 삭제는 금지한다.

즐겨찾기 양은 저장된 **단백질 g**이며 음식 중량이나 100g당 값이 아니다. 이번에는 즐겨찾기 한 항목당 1회 선택이며 배수/수량은 후속이다.

### 생성·수정·삭제

- 직접 입력/기존 기록 수정 화면에서 ‘즐겨찾기에도 저장’ 선택을 제공한다. 기록 저장/수정과 즐겨찾기 생성은 **동일 modify**로 성공하거나 실패한다. 별도 저장을 먼저 해서 기록 실패 후 즐겨찾기만 남게 하지 않는다.
- 기존 기록과 즐겨찾기 사이 영속 참조가 없으므로 연결 상태처럼 보이는 별 토글은 만들지 않는다. 목록의 명시적 편집·삭제가 즐겨찾기 원본을 관리한다.
- 즐겨찾기 편집은 목록 내 별도 편집 화면/모드로 전환한다. 선택한 음식이 있으면 먼저 선택 버리기 확인을 거친다. 기존 추가 시트 위에 편집 시트를 연속으로 쌓지 않는다.
- 편집 입력은 저장된 이름·값을 보여주되 저장 검증은 새 기록과 같은 양수 파서다. ID·legacySourceID·position은 보존하고, 사용자가 확인한 이름·값만 변경한다. 이관 캡처/백업은 수정하지 않는다.
- 편집 취소·스와이프·저장 실패는 기존 편집 안전 정책을 재사용한다. 저장 성공은 목록으로 돌아가며 일일 섭취 기록을 생성하지 않는다.
- 삭제는 저장된 이름·값을 확인한 뒤 해당 favorite ID만 제거한다. ‘기존 섭취 기록은 유지’ 문구를 표시한다. 다른 중복 즐겨찾기나 과거 기록을 지우지 않는다. 삭제 취소는 write 0.

새 생성 시 이름 trim 결과와 centigrams가 정확히 같은 기존 항목이 있으면 새 즐겨찾기만 만들지 않고 기존 항목을 재사용한다. 요청한 일일 기록 저장은 정상 진행하고 ‘이미 즐겨찾기에 있음’으로 알린다. 같은 이름·다른 양은 별도 항목으로 허용한다. 대소문자/동의어를 임의로 합치거나 기존 중복 항목을 자동 병합하지 않는다. 명시적 즐겨찾기 수정도 다른 기존 중복을 삭제하지 않는다.

### position 규칙

조회는 원래 position을 보존한다. 추가는 마지막 position 다음 값을 checked arithmetic으로 할당한다. Int 범위를 넘는 경우에만 기존 순서를 유지한 연속 position 재배정을 같은 트랜잭션에서 수행한다. 삭제 후 반드시 전체 재번호를 할 필요는 없지만 배열은 항상 position 순서와 일치해야 한다. ID와 legacySourceID는 재배정하지 않는다.

## A: 다중 기록 추가의 원자성

선택 시점에 favorite ID·이름·단백질량과 고정 대상 날짜를 스냅샷으로 보관한다. 각 선택 항목의 새 record ID는 세션에서 고정한다. 같은 항목 선택 해제 후 재선택, 실패 후 재시도에서도 아직 커밋되지 않은 ID를 유지한다. operation ID는 기존처럼 저장 시도마다 새로 생성한다.

하단 요약은 checked sum으로 합산한다. 한 번의 `store.modify` 안에서 최신 데이터와 선택 스냅샷을 검사하고 모든 FoodRecord를 같은 날짜에 추가한다. 일부 항목이 삭제/수정됐으면 조용히 건너뛰거나 양을 바꾸지 말고 전체 write를 중단해 선택 재확인을 요구한다. 빈 선택·중복 선택/record ID·부적합한 양·합계 overflow도 전체 실패다.

도메인의 `DailyLog`와 원본 총량·signed 보정 계약을 재사용한다. 즐겨찾기에서 가져온 식품은 기존 `.favorite`, 검색 결과는 기존 `.search` source를 사용한다. 즐겨찾기는 단백질량 템플릿으로 음식 기준중량이 없으므로 quantity를 추정하지 않는다. 기존 총량을 UI에서 별도로 누적 저장하지 않는다. 원자적 작업 실패는 0행, 성공은 N행이다.

## 모든 쓰기의 작업 종류 구분

새 쓰기를 기존 ‘기록 저장 성공 → 시트 닫기’ callback에 무조건 연결하면 즐겨찾기 관리·검색 이력 저장 때도 편집 화면이 닫힌다. A부터 명시적인 세션 작업 문맥을 설계한다.

| 작업 | 확인된 성공 / 재확인 반영 | 미반영 / 교체 전 실패 |
| --- | --- | --- |
| 직접 기록·다중 기록 추가(선택적 favorite 포함) | 최신 상태 반영 후 추가 시트 닫기 | 현재 초안·선택·record/favorite ID 유지, 재시도 가능 |
| favorite 수정 | 수정 모드에서 목록으로 복귀 | 편집 값 유지, 재시도 가능 |
| favorite 삭제 | 목록 유지, 선택/대상 행 갱신 | 기존 행 유지, 삭제 완료라고 말하지 않음 |
| 검색 이력·언어 설정(B) | 해당 상태만 갱신, 추가 시트 닫지 않음 | 검색 입력/결과 보존, 쓰기 실패를 검색 실패로 표현하지 않음 |

전역 busy와 pending 잠금은 기록·목표·favorite·이력·언어 설정을 모두 포함한다. pending 재확인은 load만 수행한다. 시트가 남아 있으면 원래 작업 문맥에 따라 성공 후처리하고, 닫혔다면 홈 배너에서 상태만 반영한다. 시트가 사라진 뒤 초안/선택 복원을 약속하지 않는다. 홈 미반영 문구도 특정 기록 추가에 한정하지 않는 중립 문구를 사용한다.

pending 상태로 닫을 때 이미 시도한 삭제·이력 저장을 취소했다고 설명하지 않는다. `PendingSave`가 지금 operationID/day만 갖는다는 점을 고려해 작업 문맥은 런타임 세션에 추가할 수 있지만 저장 schema에 pending/초안을 영속화하지 않는다.

## B: 공급자와 검색 결과 계약

### 구현 전에 확인할 외부 사항

영어 파일의 출처·기준량·배포 이용 조건과 한국 API의 현재 문서·응답 샘플·단백질 단위·기준량·HTTPS 지원·인증·페이지 제한을 확인하고 근거를 증거 문서에 남긴다. 저장소에 없는 내용을 사실로 가정하지 않는다. API 키 값은 문서·로그·테스트 fixture에 넣지 않는다.

이 확인 전 기존 strings를 따라 모든 행에 ‘100g당’을 붙이지 않는다. 결과 모델은 공급자별 stable ID, 이름, 단백질 값, 기준량/단위, 출처 식별, 검증 상태를 갖는다. 로컬 ID는 매 검색 UUID나 이름만으로 만들지 않고 고정된 카탈로그 행 식별 방식으로 유지한다. 동명이품목을 자동 합치지 않는다.

확인된 기준량에 대한 1회분을 선택하면 그 기준량과 단백질량을 모두 보여준다. 임의 섭취 중량·배수 환산은 후속이며, 이번 선택은 결과에 명시된 기준량 1회분이다. 기록에는 검증된 기준량을 기존 `FoodQuantity`의 해당 단위로 보존한다(예: gram 100). 지원되지 않거나 해석할 수 없는 단위는 임의 gram/serving으로 치환하지 않고 자동 추가를 차단한다. 기준량을 확인할 수 없는 결과는 이름을 직접 입력으로 복사하는 경로만 제공하고 검증되지 않은 단백질량은 prefill하지 않는다. 해당 결과를 선택·자동 기록하지 않는다. 이 fallback만으로 그 공급자의 검색 연결 완료를 선언하지 않는다.

단백질 0 또는 음수·NaN·범위 초과·숫자 아님은 결과에서 구분하고 현재 양수 기록 계약에 따라 선택을 차단한다. 영문 JSON의 부동소수 표기를 그대로 Double 곱셈으로 누적하지 말고 Decimal 기반 centigram 변환을 사용한다. 두 자리 초과 정밀도는 가장 가까운 centigram으로 반올림(양수 절반 올림), 반올림 전후 양수·범위/overflow를 검사한다. 출처값과 표시·저장값이 다른 경우 반올림된 양임을 설명한다.

### 검색 실행

`FoodSearchProvider`와 공급자 응답 adapter를 UI에서 분리한다. 영어는 trim된 검색어를 이름의 대소문자·발음부호 무시 부분 일치로 필터하고 원래 카탈로그 순서를 유지한다. 빈 검색어는 모든 식품을 반환하지 않고 기존 검색 이력을 보여준다.

한국 검색은 URLComponents 등 안전한 경로/파라미터 인코딩, HTTP 상태·API 오류코드·row 없음·디코드 실패·timeout을 명시적으로 처리한다. 앱 키 누락이면 무한 로딩 대신 검색을 사용할 수 없다는 안내와 직접 입력 경로를 제공한다. 기존 최초 5건 제한을 몰래 전체 결과라고 표시하지 말고, 확인한 API 계약에 맞춘 페이지 또는 더 보기 상태를 제공한다.

명시적 검색 실행마다 이력 저장을 시작하기 전에 request ID와 언어·query를 고정한다. 이력 저장 callback에서 네트워크를 시작하기 직전에도 현재 request ID와 시트 생존 상태를 확인한다. 닫힌 시트의 지연 callback이 새 검색을 시작하지 않도록 한다. 새 검색·언어 변경·시트 닫기 시 이전 요청을 취소하고, 취소가 늦어져 도착한 응답도 ID 비교로 폐기한다. 실패·빈 결과·로딩을 구분하며 모든 종료 경로에서 로딩을 끝낸다. 영어 파일 로드 실패를 네트워크 오류라고 안내하지 않는다.

선택한 결과가 있으면 새로운 검색 실행 또는 언어 변경 전에 ‘선택을 버리고 검색/변경’ 확인을 받는다. 검색창 입력만으로 기존 선택을 숨기거나 바꾸지 않는다. 확인 전에는 기존 결과와 선택 기준 query가 유지된다. 검색 선택 다중 추가는 A의 동일 원자적 기록 경로를 사용한다.

## B: 최근 검색과 검색 언어

최근 검색의 의미는 기존처럼 **사용자가 명시적으로 실행한 검색어**다. 음식을 실제 기록한 검색어만 저장하는 방식으로 조용히 바꾸지 않는다. 키 입력마다 저장하지 않는다. 최근 행 탭도 명시적 재검색이다.

검색 이력 저장은 별도 명시적 `perform` 작업이다. 현재 busy/pending이면 새 검색 실행 버튼도 차단하고 저장 결과 확인을 먼저 제공한다. 검색 실행 시 trim 후 빈 문자열을 거부하고 query/언어를 고정한 뒤 이력 저장을 한 번 요청한다. 이력 저장 완료/교체 전 실패/미확정 결과를 처리한 후 검색 요청을 실행할 수 있으며, 네트워크 성공 여부와 이력 저장 성공 여부는 분리해 안내한다. 미확정이어도 결과를 읽어 보여줄 수는 있지만 모든 추가·관리 쓰기는 잠근다. 재확인 뒤 자동으로 검색 이력을 재저장하지 않는다.

새 검색어와 trim 결과가 정확히 같은 기존 항목이 있으면 position이 앞선 항목 하나의 ID/sourceID를 유지해 맨 앞으로 이동한다. 기존 다른 중복·빈 검색어를 자동 삭제하지 않는다. 이력 이동 시 안정 순서를 유지한 0부터 연속 position을 같은 modify에서 부여한다. 조회만으로 기존 순서를 바꾸거나 시각을 만들어내지 않는다. 표시 개수를 제한해도 데이터 자체를 오래됐다는 이유로 잘라내지 않는다. 필요하면 더 보기로 모든 항목에 접근한다.

빈 기존 검색어는 표시용 대체 문구·재검색 비활성·명시적 삭제를 제공한다. 이력 삭제는 해당 ID만 제거하고 기록·즐겨찾기는 건드리지 않는다. 이력 삭제의 pending도 위 작업별 후처리를 적용한다.

언어 선택은 검색 탭에 최소 한국어/영어 선택 UI를 둔다. UI 언어와 음식 검색 언어를 구분하고 `state.settings.searchLanguage.resolved`를 초기값으로 사용한다. 변경은 선택 버리기 확인 후 명시적 설정 저장으로 처리한다. 확인된 상태만 언어 표시와 공급자에 적용하며 저장 실패/미확정에서는 이전 공급자를 유지한다. 새 선택의 저장 raw 형식은 현재 `SearchLanguageSetting.interpret`가 해석하는 값과 일치시키고 무관한 이관 캡처를 수정하지 않는다.

## 완료 기준과 인계

A는 즐겨찾기의 기존 데이터가 보존되고 관리·기록 재사용·원자적 다중 추가·작업별 재확인이 검증돼야 완료다. B는 기준량이 확인된 공급자 검색과 최근 검색/언어 저장까지 검증돼야 완료다. 검색 공급자 조사만 했거나 fallback만 연결한 것을 전체 완료로 표시하지 않는다.
