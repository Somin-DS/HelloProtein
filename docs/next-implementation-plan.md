# 다음 구현 계획: 기존 데이터 이관과 날짜별 기록 영속화

작성일: 2026-09-28. 대상: 이 작업 폴더를 인계받는 구현 AI 에이전트.

이 문서는 **다음 한 단계의 구현 지시서**다. 문서 작성 시 제품 코드는 변경하지 않았으며, 아래 작업은 아직 구현하거나 검증하지 않은 계획이다. 전체 리뉴얼, Android 출시, 결제 도입까지 한 번에 진행하는 지시가 아니다.

## 1. 목표와 인계 방법

기존 Realm/UserDefaults 데이터를 손실 없이 새 저장소에 한 번만 이관하고, SwiftUI 기록 화면에서 날짜별 조회·추가·수정·삭제한 결과가 앱 재실행 후에도 유지되도록 한다. 이관 도중 중단되거나 저장이 실패해도 원본과 마지막 정상 기록을 보존해야 한다.

구현 에이전트에게 다음과 같이 전달한다.

> 이 작업 폴더의 현재 변경 사항 전체를 기준으로 `docs/next-implementation-plan.md`를 순서대로 구현해줘. 먼저 실제 코드와 지침을 확인하고, 데이터 보존 계약 → 저장소 → 이관 → 화면 연결 → 검증 순으로 진행해줘. 기존 변경을 되돌리지 말고, 범위 밖의 Android·AI·구독 구현은 하지 마. 통과한 검사와 미검증 항목을 구분해서 보고해줘.

**반드시 현재 작업 폴더 전체를 전달한다.** 핵심 패키지와 화면 파일 대부분이 아직 untracked 상태다. Git HEAD만 checkout하면 이 문서가 전제하는 코드가 없다. 비밀 파일이나 실제 사용자 데이터는 전달물에 포함하지 않는다.

## 2. 이번 작업 범위

### 포함

1. 원본 백업 및 읽기 경계, 데이터 매핑 계약, 이관 실패 상태 정의.
2. 기록·즐겨찾기·검색 이력·설정·목표·이관 메타데이터의 일관된 영속 저장.
3. 중단 후 재실행 가능한 이관 조정자와 원자적 완료 처리.
4. 저장소를 주입받는 SwiftUI 기록 화면과 안전한 시작 경로.
5. 과거 날짜 탐색과 기록 편집, 합계만 남은 과거 날짜의 표시·합계 수정.
6. 단위 테스트, 격리된 Realm 통합 테스트, 시뮬레이터 재실행 검증.

### 제외

- Android 앱/SDK 설치, Compose·Flutter·공통 UI 기술 확정.
- AI 입력, 사진 분석, 서버, 계정, 클라우드 동기화.
- 광고, StoreKit, 구독, 체험 차감. 기존 무료 기능 제한 도입.
- 통계 그래프·전체 설정·검색·즐겨찾기 화면의 전면 리뉴얼.
- Realm 및 외부 패키지 일괄 업그레이드, 기존 UIKit 전체 재작성.
- 최소 지원 OS 변경, App Store 배포, 원본 데이터 삭제.

Swift 코어의 데이터 계약은 Android 구현에 참고할 수 있지만 Swift 패키지가 곧 Android 공통 런타임은 아니다. JSON 저장 방식도 양 플랫폼의 최종 저장 기술로 확정하지 않는다.

## 3. 현재 상태와 신뢰할 수 있는 검증 범위

| 영역 | 현재 구현 | 다음 작업에서 해결할 것 |
| --- | --- | --- |
| `MigrationCore` | 스냅샷 검증·변환, 원본 날짜/순서 보존 | 실제 저장소 매핑, 충돌 처리, 이관 실행 |
| `LegacyRealmSnapshotReader` | Realm/UserDefaults 값을 읽어 변환기에 전달 | 실제 읽기 전용 보장, 백업, 일관된 추출 |
| `HelloProteinCore` | 날짜·음식·목표·일별 합계·signed 보정값 | 입력/변경 불변조건 보강, 전체 저장 상태 |
| `FileRecordRepository` | 일별 기록 JSON 저장, 파일 원자적 교체 | 이관 완료와 전체 데이터의 단일 커밋 |
| `RecordHomeViewModel` | 날짜 선택·추가·수정·삭제 | 현재 메모리 사전만 사용하므로 저장소 연결 |
| SwiftUI 프로토타입 | 날짜 줄·합계·기록 편집 시트 | 저장 실패 UX, 실제 목표, 과거 합계 편집 |
| 앱 시작 | 기존 UIKit/스토리보드 | 기존 자동 초기화보다 먼저 실행되는 시작 게이트 |

이전 작업 보고상 `MigrationCore` 15개, `HelloProteinCore` 15개 테스트 및 iOS 시뮬레이터 대상 전체 빌드가 통과했다. 이 계획 작성 중 재실행하지 않았다. **앱 실행, 실제 사용자 Realm 파일, 실제 업그레이드, Android는 미검증**이다.

설치된 Xcode는 이전 확인 기준 27.1이며 `/Users/somin/Downloads/Xcode.app`에 있다. 프로젝트는 iOS 13 설정을 유지하고, 기존 성공 빌드에서 명령행으로만 iOS 15를 지정했다. SwiftUI 프로토타입은 iOS 15 이상이다.

주의: `update-roadmap.md`가 가리키는 `/private/tmp/helloprotein-baseline-build.log`를 최신 성공 증거로 간주하지 않는다. 이전 실패 로그일 수 있다. 새 검증은 별도 로그와 실제 종료 코드를 남긴다.

## 4. 구현 전 확인할 결함과 경계

- `ShowViewController.viewWillAppear`의 날짜 변경 처리가 `DailyProtein`을 삭제한다. 이관 전에 이 화면이 실행되면 원본을 잃을 수 있다.
- `SceneDelegate`에서 분기만 추가해도 충분하다고 가정하지 않는다. `Info.plist`의 scene storyboard와 프로젝트의 main storyboard 설정으로 구 화면이 먼저 생성될 수 있다. 구 화면에는 `try! Realm()` 초기화도 있다.
- `LegacyRealmSnapshotReader.readDefault()`는 `Realm()`을 연다. 주석과 달리 기본 호출만으로 읽기 전용이 보장되지 않으며, 파일 생성이나 스키마 처리 가능성을 확인해야 한다.
- 현재 builder는 추출 중 검증에 실패하면 스냅샷을 반환하지 않는다. **검증 이전의 원본 확보 단계**를 분리해야 한다.
- UserDefaults의 `integer(forKey:)`는 잘못된 타입을 0으로 해석할 수 있다. 누락, 명시적 0, 잘못된 타입을 구분한다.
- 파일 저장소는 일별 기록만 저장한다. `.atomic`은 별도 완료 플래그·설정·백업까지 하나의 트랜잭션으로 묶지 않는다.
- 현재 잠금은 저장소 인스턴스별이다. 여러 인스턴스의 읽기→수정→저장 경쟁을 막지 못한다.
- `FoodRecord`의 공개 변경 속성으로 생성자 검증을 우회할 수 있다. 예를 들어 생성 후 단백질을 0으로 바꿀 수 있다.
- 구 데이터 변환기는 음수 값을 보존하지만 새 음식 모델은 0/음수를 거부한다. 매핑 실패를 삭제나 0 보정으로 해결하면 안 된다.
- 날짜 문자열·수량 파싱은 전체 문자열 검증을 강화해야 한다. `Decimal(string:)` 성공만으로 유효한 입력으로 판단하지 않는다.
- 현재 편집은 기존 `source`, `quantity`를 잃고 수동 입력으로 재생성한다. 저장 실패에도 시트가 닫힌다.
- 현재 합계 계산 실패를 0으로 표시하고, 목표 진행률은 100g으로 고정한다. 데이터 오류를 정상 빈 상태처럼 표시하면 안 된다.

## 5. 책임 분리와 의존성

권장 흐름:

```text
앱 시작 게이트
  → iOS 이관 조정자
      → 원본 백업 / Realm·UserDefaults 어댑터
      → MigrationCore 검증
      → 새 모델 매퍼
      → 전체 저장소 단일 커밋
  → 저장소를 주입받은 SwiftUI 화면
      → ViewModel / 기록 편집 유스케이스
      → HelloProteinCore / 저장소
```

- `MigrationCore`: 원본 값과 검증 규칙. UIKit·SwiftUI·Realm 의존 금지.
- `HelloProteinCore`: 새 모델·저장 계약·합계 규칙. 화면과 구 DB를 알지 않는다.
- 앱의 이관 계층: 두 코어를 연결하며 iOS 파일 위치, 백업, 실행 순서를 담당한다.
- 앱 전체에서 새 저장소의 쓰기 소유자를 하나로 유지한다. 직렬 큐 또는 지원 OS에 맞는 동시성 방식으로 **읽기→수정→저장 전체**를 직렬화한다. UI는 메인 실행 문맥에서 갱신한다.
- 저장소 위치·시계·시간대·ID 생성기·파일 쓰기 구현을 주입 가능하게 하여 실패와 날짜 경계를 테스트한다.

## 6. 저장 파일과 커밋 계약

현재 schema 1이 기록만 저장하므로 전체 상태용 schema 2 도입을 기본안으로 한다. 구체적인 타입명은 변경 가능하나 다음 데이터는 같은 커밋에 들어가야 한다.

| 필드 | 필수 의미 |
| --- | --- |
| `schemaVersion` | 알 수 없는 버전은 실패. 빈 저장소로 대체 금지 |
| `logs` | 날짜별 음식, signed 레거시 보정값, 원본 연결 정보 |
| `favorites` | 기존 ID·이름·단백질·순서 보존 |
| `searchHistory` | 기존 ID·문자열·순서 보존 |
| `settings` | 검색 언어, 기존 목표 원문 등 복구에 필요한 값 |
| `goals` | 적용 시작일이 명시된 목표 이력 |
| `migration` | 신규 설치/레거시 이관 출처, 이관 버전, 완료 시각, 원본 지문, 검산 결과 |

완료 마커를 UserDefaults에 따로 쓰지 않는다. **모든 이관 데이터와 완료 메타데이터를 하나의 최종 파일 교체로 커밋**한다. 준비 중 상태와 백업은 별도 파일일 수 있지만 완료 판정의 근거가 되어서는 안 된다.

쓰기 순서:

1. 전체 후보 상태를 메모리에서 만들고 도메인·중복·합계·개수 검증.
2. 목적 파일과 같은 파일시스템의 임시 파일로 인코딩/쓰기.
3. 임시 파일을 다시 디코딩해 구조·값·이관 메타데이터 검산.
4. 최종 파일을 원자적으로 교체. 쓰기 실패 시 이전 정상 파일 유지.
5. 최종 파일을 읽어 확인한 다음 화면 진입. 이 확인 실패 시 복구 상태로 전환.

백업과 저장 파일은 앱 전용 영속 디렉터리에 둔다. 캐시나 임시 디렉터리를 유일한 보관처로 사용하지 않는다. iOS 파일 보호 설정과 잠금 상태에서의 실패를 명시적으로 다룬다. 데이터 보호 때문에 읽지 못하는 상황도 빈 데이터가 아니다. 원자적 교체와 물리적 전원 차단 내구성을 같은 것으로 주장하지 않는다.

기존 schema 1 파일이 발견되면 먼저 백업한다. 기록을 보존하는 schema 변환 경로를 제공하고, 레거시 원본도 함께 존재하는 경우 자동 덮어쓰기·임의 병합하지 않는다. 겹치는 날짜/ID 처리 규칙이 검증되지 않았다면 명시적 충돌 상태로 멈춘다.

## 7. 원본 확보와 이관 상태 전이

### 원본 확보

1. 시작 게이트에서 기존 Realm/UserDefaults 쓰기와 날짜 초기화를 차단한다.
2. 기존 파일 존재 여부와 관련 defaults 키의 실제 타입을 확인한다. 파일이 없는데 기본 `Realm()`을 열어 빈 파일을 만들지 않는다.
3. 검증·정규화 이전에 원본 Realm 및 관련 defaults 값을 보관한다. 날짜 객체, 숫자 타입, 원문 문자열을 보존할 수 있는 형식을 사용한다.
4. 열려 있는 Realm 파일을 단순 파일 복사하지 않는다. 고정된 Realm 버전이 지원하는 안전한 snapshot/copy API 또는 파일이 열리기 전의 일관된 복사 방식을 확인해 사용한다. 필요 시 동반 파일 요구사항도 확인한다.
5. 원본 자체에 자동 스키마 변경을 유발하지 않는 읽기 방식을 검증한다. 필요하면 확보한 복사본에서 읽는다.
6. 백업 성공을 확인한 뒤 정규화와 매핑을 진행한다. 실패 시 원본을 수정하거나 삭제하지 않는다.

원본 지문은 Swift `hashValue`가 아닌 안정적인 직렬화와 SHA-256 등 재실행 가능한 방식으로 만든다. 캡처 시각을 제외한 원본 값·순서·타입 등 지문 입력 규칙을 명시한다. 음식 이름과 기록 내용을 콘솔/분석 로그에 출력하지 않는다.

### 시작 시 판단

| 상태 | 처리 |
| --- | --- |
| 유효한 완료 저장소 있음 | 새 저장소 사용. 구 데이터를 재이관하지 않음 |
| 완료 후 사용자가 수정한 저장소 | 그 수정본이 기준. 구 원본 지문이 달라도 덮어쓰지 않음 |
| 새 저장소 없음 + 유효한 구 데이터 있음 | 백업→검증→매핑→단일 커밋 |
| 새 저장소 없음 + 구 데이터도 없음 | 신규 설치용 빈 상태를 명시적으로 생성 |
| 기록 없이 목표/즐겨찾기만 있음 | 기존 사용자로 분류하고 해당 데이터 이관 |
| 임시 파일/준비 중 백업만 있음 | 완료로 간주하지 않음. 검증 가능한 원본에서 재시도 |
| 새 저장소 손상/미지원 버전/불완전 메타데이터 | 복구 화면. 자동 초기화 및 구 데이터 덮어쓰기 금지 |
| 기존 완료 증거가 있는데 최종 파일 없음 | 손실 상태로 처리. 신규 설치로 분류 금지 |
| 날짜 충돌·타입 오류·표현 불가능한 값 | 원본 보존 후 구체적인 복구 상태 |

완료 파일 자체가 사라진 경우와 진짜 신규 설치를 구분하기 위한 보조 증거 정책도 설계한다. 예를 들어 보관된 이관 백업/출처 기록을 활용하되, 별도 플래그를 커밋 성공의 유일한 기준으로 삼지 않는다. 증거가 전혀 없으면 과거 완료 여부를 알아낼 수 없다는 한계를 보고한다.

중단 주입 지점: 백업 전, 백업 후, 변환 후, 임시 파일 쓰기 중, 최종 교체 직전, 교체 직후, 첫 화면 진입 직전. 각 지점에서 다음 실행 결과가 ‘이전 정상 상태’ 또는 ‘완료된 새 상태’로 귀결되어야 한다. 재시도는 ID와 기록 수를 늘리지 않는다.

## 8. 데이터 매핑 계약

| 구 데이터 | 새 데이터 / 보존 규칙 |
| --- | --- |
| `DailyProtein` | `lastSavedDay`의 음식 기록. 이관 실행일에 넣지 않음 |
| `totalIntake` | 해당 날짜 상세 합계와의 차이를 signed 보정값으로 저장 |
| `StatProtein` | 해당 날짜의 합계 전용 기록. 음식 상세를 만들어내지 않음 |
| `Favorites` | 별도 즐겨찾기 컬렉션에 ID·이름·양·순서 보존 |
| `SearchHistory` | 검색어와 ID·순서 보존. 임의 중복 제거 금지 |
| `targetProtein` | 원문 보존 + 유효할 때 현재 목표로 변환 |
| `searchLanguage` | 원문 보존. 미지원 값은 명시적 fallback과 원문을 함께 유지 |
| `date` / `Date` | 날짜 라벨·원본 시각 보존. 일자 판정 근거를 기록 |

ID는 `legacy:daily:<ObjectId>`처럼 컬렉션별 namespace를 사용해 결정적으로 매핑한다. 원본 ID도 추적 가능하게 보관한다. 문자열 정규화로 이름 원문을 잃지 않도록 원본 감사 정보와 화면 표시값을 구분한다.

단위는 새 계약의 0.01g 정수다. 구 정수 g를 `Int64`로 변환하고 ×100 연산까지 overflow를 검사한다. JSON을 향후 JavaScript 도구에서 읽을 수 있다는 이유만으로 Int64를 Double로 경유하지 않는다.

합계 예시:

- 구 음식 합계 45g, 구 총량 55g → 음식 45g + 보정값 10g.
- 구 음식 합계 20g, 구 총량 15g → 음식 20g + 보정값 -5g. 0으로 clamp 금지.
- 과거 합계만 70g → 상세 없음, 보정값 70g. 새 음식 10g 추가 후 총량 80g.
- 위 날짜에서 사용자가 **하루 총량을 75g으로 수정**하면 보정값은 `75 - 상세 합계 10 = 65g`. 총량 75g을 보정값으로 그대로 쓰지 않는다.

레거시 합계 편집은 원본 가져오기 값과 사용자 수정 사실을 구분해 보관한다. ‘이전 기록 합계’와 ‘새로 추가한 음식’을 함께 보여주되 보정값을 가짜 음식으로 표시하지 않는다. 음수 보정값을 양수 음식처럼 표현하지 않는다.

### 애매하거나 잘못된 원본

- 중복 ID, 동일 날짜의 중복 과거 합계, 현재 기록 날짜와 과거 합계 충돌은 임의 합산·최신 선택하지 않는다.
- 날짜 근거가 없는 음식은 오늘로 옮기지 않는다. 원본 백업 후 복구 대상이다.
- 기록이 없고 `totalIntake == 0`만 남은 경우와 날짜가 누락된 실제 기록을 구분한다. 빈 상태 판정 조건을 fixture로 명시하고 변환기에 반영한다.
- 0/음수 음식처럼 새 정상 음식 모델로 표현할 수 없는 원본은 **이번 단계의 기본 정책으로 이관을 중단하고 복구 상태에 둔다**. 백업만 해 놓고 전체 이관 완료로 표시하지 않는다. 값 삭제·절댓값·합계 보정으로 상세를 숨기는 방식은 금지한다.
- 원본이 정상인데 모델 제약만 문제라면 lossless 레거시 전용 표현을 별도 설계할 수 있다. 이 경우 표시·편집·검산까지 함께 구현하고 정책 변경 이유를 보고한다.
- 잘못된 목표는 원문을 보존하고 ‘목표 확인 필요’로 표시한다. 기록을 숨기거나 기존 사용자를 초기 온보딩으로 되돌리지 않는다.

### 날짜와 목표

- 저장 날짜는 Gregorian `YYYY-MM-DD`, ASCII 숫자, 연도 0001~9999, 실제 존재하는 날짜로 제한한다.
- 지역화된 요일은 날짜 판정에 사용하지 않는다. 저장된 날짜 라벨과 시각이 충돌하면 원래 시간대를 알 수 있는지부터 확인하고, 현재 시간대로 임의 재해석하지 않는다.
- 이미 저장한 일자는 시간대 변경 후에도 바뀌지 않는다. ‘오늘’ 계산만 주입된 현재 시각·시간대와 Gregorian calendar를 사용한다.
- 기존 목표의 과거 적용 시점은 알 수 없다. 가져온 목표는 이관일 적용으로 기록하고, 그 이전 날짜의 목표 달성률은 ‘목표 이력 없음’으로 처리한다.
- 같은 적용일에 목표가 중복되면 ID 문자열 순서로 하나를 선택하지 않는다. 사용자 변경은 해당 일자 목표를 교체하고, 외부/디코딩 중복은 검증 실패로 처리한다.

## 9. 도메인과 입력 검증

1. 생성 후 속성 대입으로 잘못된 음식이 저장되지 않도록 불변 값 또는 검증된 변경 API를 사용한다. 저장 경계에서도 전체 모델을 검증한다.
2. 날짜·수량·단백질 입력은 전체 문자열을 검사한다. `12abc`, 지수 표기, NaN, 무한대, 부호 혼입을 정상 입력으로 취급하지 않는다.
3. 신규 단백질 입력은 양수, 소수점 이하 최대 2자리로 한다. 이번 단계에서는 초과 자릿수를 조용히 반올림하지 않고 안내한다.
4. 지역별 소수점 기호를 지원하되 천 단위 구분자는 받지 않는다. `1,234`를 기계적으로 `1.234`로 바꾸지 않는다. 저장 표현은 지역과 무관하게 정규화한다.
5. 개별 값·합계·단위 변환에서 overflow를 검사한다. 임의의 영양학적 상한선을 도입하지 않는다.
6. `MigrationPlan`을 디코딩했다는 이유로 검증 완료로 취급하지 않는다. 스키마와 불변조건을 다시 확인한다.

## 10. SwiftUI 연결과 사용자 흐름

### 시작 경로

- 이번 단계의 새 흐름은 명시적인 개발/검증용 진입 설정으로 활성화한다. 실제 사용자의 실행 경로를 무조건 새 화면으로 바꾸는 출시 전환은 별도다.
- 새 흐름에서는 storyboard 자동 생성 이전에 시작 게이트가 주도권을 가져야 한다. 필요하면 공통 시작 화면을 코드로 구성하고 기존 경로도 명시적으로 생성한다.
- iOS 13/14에서는 이관을 시작한 뒤 지원하지 않는 SwiftUI 화면으로 보내지 않는다. 기존 경로 유지와 API availability를 검증한다.
- 같은 앱 데이터 영역에 새 저장소를 만든 뒤 다시 구 앱 경로로 돌아가 쓰는 상황을 허용하지 않는다. 이관 완료 후 구 경로 진입을 차단하거나, 검증용 별도 데이터 위치/설치로 분리한다. 자동 역이관은 구현하지 않는다.
- 복구 화면에는 문제 유형, 원본이 보존되었다는 사실, 재시도 동작을 제공한다. ‘초기화’ 버튼이나 자동 원본 삭제는 만들지 않는다.

### 기록 화면

- 저장소에서 선택 날짜를 로드한다. 7일 줄 외에 날짜 선택기를 제공하여 오래된 날짜로 직접 이동할 수 있게 한다.
- 편집 시트를 열 때 대상 날짜와 기록 ID를 고정한다. 화면 날짜가 바뀌거나 자정이 지나도 다른 날짜에 저장하지 않는다.
- 편집은 기존 기록의 ID·날짜·source·quantity를 유지하며 사용자가 바꾼 필드만 변경한다.
- 후보 상태 생성 → 저장 성공 → 화면 상태 반영 순서를 지킨다. 실패 시 이전 화면 데이터와 입력 내용을 유지한다.
- 저장/삭제 성공 시에만 시트를 닫는다. 처리 중 중복 실행을 막고, 취소는 저장하지 않는다.
- 입력 오류, 파일 접근 실패, 손상 데이터는 서로 다른 메시지로 안내한다. 합계 오류를 0으로 숨기지 않는다.
- 실제 목표가 있는 날짜에만 진행률을 표시한다. 목표가 없으면 합계는 그대로 보여주고 목표 미설정/이력 없음 상태를 표시한다. 동작 없는 ‘목표량 수정’ 텍스트는 제거하거나 실제 동작을 연결한다.
- 합계 전용 과거 기록과 상세가 섞인 기록 모두 레거시 합계 영역을 표시한다. 합계 전용 날짜에 일반 빈 기록 안내만 표시하지 않는다.
- 레거시 하루 총량 수정은 일반 음식 편집과 다른 시트로 제공하고, §8의 보정값 계산 규칙을 적용한다. 삭제는 사용자 추가 음식 삭제와 원본 합계 제거를 혼동하지 않도록 이번에는 음식 삭제만 제공한다.
- 이번에 변경하는 문구는 최소 영어/한국어로 리소스화한다. 접근성 이름, 큰 글자, 음수/소수 합계의 레이아웃을 확인한다. 전체 앱 번역은 범위 밖이다.

## 12. 실행 순서와 단계별 통과 조건

### A. 시작 상태와 계약 확정

`AGENTS.md` 등 적용 지침, Git 변경 상태, 소스/테스트를 확인한다. 기존 변경을 보존한다. 실제 출시 버전과 저장소가 같다는 가정은 하지 않는다. §6~8의 schema·상태 전이·매핑을 코드와 fixture로 명시한다.

통과 조건: 모든 원본 컬렉션과 defaults 키의 목적지가 정의되어 있고, 미지원 원본의 실패 정책이 명확하다.

### B. 코어와 저장소

도메인 불변조건 → 전체 저장 상태 → schema 검증 → 원자적 교체 → 직렬 변경 API → 실패 주입 테스트 순서로 구현한다.

통과 조건: 정상 round trip, 손상 파일, 미지원 버전, 쓰기 실패, 중복 날짜/ID, schema 1 보존을 자동 검증한다. 실패가 빈 저장소를 만들지 않는다.

### C. 원본 백업과 이관

격리된 실제 Realm fixture로 백업/읽기를 먼저 검증한다. 매퍼와 조정자를 붙이고 각 중단 지점에서 재실행한다. 완료 후 수정된 새 기록을 다시 실행한 이관이 덮어쓰지 않는지 검사한다.

통과 조건: 전체 개수·순서·ID·일별 합계·설정이 일치하고 원본이 불변이다. 새 파일과 완료 마커가 따로 성공하는 상태가 없다.

### D. 시작 경로와 화면

시작 게이트 → 저장소 주입 → 날짜 탐색 → 추가/편집/삭제 → 과거 합계 수정 → 오류 상태 순서로 연결한다. 기존 날짜 초기화가 새 흐름에서 한 번도 실행되지 않게 한다.

통과 조건: 화면 조작 후 저장소 재생성과 앱 재실행에서 같은 기록/합계를 보여준다. 실패 시 입력과 원래 값이 남는다.

### E. 시뮬레이터 검증과 인계

단위/통합 검사 후 앱을 실행한다. 정상 업그레이드, 중단 후 재시작, 오래된 날짜 편집, 저장 실패를 확인한다. 완료 조건에 따라 결과를 문서화한다.

통과 조건: 컴파일 성공과 UI 실행 성공을 구분한 증거가 있으며, 실제 사용자 데이터/실기기 등 검증하지 않은 범위를 명시한다.

## 13. 필수 검증 표

테스트 수 자체보다 아래 실패와 보존 계약을 검증하는 데 집중한다. 구현 구조를 그대로 복제하는 테스트는 피한다.

| 분류 | 시나리오 | 기대 결과 |
| --- | --- | --- |
| 정상 이관 | 음식·과거 합계·즐겨찾기·검색어·설정 모두 존재 | ID/순서/값/합계 보존 |
| 합계 차이 | 양수·음수·0 보정값 | 원래 총량과 일치, 편집 후 재계산 |
| 과거 기록 | 합계만 있는 날에 추가/편집/삭제 | 원본 합계 구분, 재실행 후 동일 |
| 총량 수정 | 합계+새 상세가 있는 날 총량 수정 | 목표 총량−상세 합계로 보정값 계산 |
| 빈 상태 | 신규 설치, 목표만 있음, 즐겨찾기만 있음, 0 기본값 | 올바른 신규/기존 사용자 구분 |
| 잘못된 원본 | 날짜 없음/중복 일자/ID/타입, 음수 음식 | 백업 유지, 부분 완료 금지 |
| 숫자 | 범위 경계, 합/곱 overflow, 접미사, 소수점 3자리 | 오류 반환, 값 변경 없음 |
| 일자 | 윤년, 잘못된 일자, 연도 범위, 비ASCII 숫자 | 엄격 검증 |
| 시간 환경 | 자정, DST, 여행 시간대, 비Gregorian 기기 설정 | 기존 일자 고정, 오늘만 올바르게 계산 |
| 목표 | 원문 문자열/숫자, 잘못된 값, 동일 적용일 | 원문 보존, 과거 달성률 추정 금지 |
| 파일 | 손상/미지원 schema/읽기 거절/쓰기 실패 | 기존 파일 보존, 오류 표시 |
| 버전 전환 | schema 1 기록과 구 원본이 공존 | 기록 덮어쓰기 없이 충돌 처리 |
| 재시도 | 각 중단 지점 후 조정자 재생성 | 중복 없이 같은 최종 상태 |
| 완료 이후 | 이관 후 사용자 편집→이관 재실행 | 사용자 편집 보존 |
| 동시 변경 | 두 편집 요청/연속 저장/중복 탭 | 순서 보장, 갱신 손실 없음 |
| 화면 오류 | 저장/삭제 실패, 취소 | 시트 입력/기존 데이터 유지 |
| 원본 보존 | 이관 전후 원본 비교 | Realm 논리 값/defaults 값 불변 |
| 시작 순서 | 새 흐름 진입, 앱 foreground 복귀 | 구 삭제/초기화 코드 미실행 |

실제 Realm 통합 테스트는 임시 파일 URL과 독립 UserDefaults suite를 사용한다. 사용자 기본 Realm이나 실제 defaults에 fixture를 쓰지 않는다. 테스트 자신이 만든 파일만 정리한다. 파일 바이트 비교가 Realm 동작 특성상 부적절하면 논리 값 비교와 백업 해시를 구분해 보고한다.

순수 오류 주입 테스트는 실제 프로세스 종료 검증을 대체하지 않는다. 시뮬레이터에서는 디버그 중단 지점으로 프로세스를 종료/재실행해 최종 교체 전후를 최소 1회씩 확인한다. 이것을 실제 전원 차단 검증이라고 보고하지 않는다.

## 14. 검증 명령과 실행 증거

현재 기준 코어 명령:

```sh
swift test --package-path MigrationCore --scratch-path /private/tmp/helloprotein-migration-tests
swift test --package-path HelloProteinCore --scratch-path /private/tmp/helloprotein-core-tests
```

기존 성공 기준 앱 빌드:

```sh
xcodebuild -project ProteinTracker/ProteinTracker.xcodeproj \
  -scheme ProteinTracker \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /private/tmp/helloprotein-baseline-build \
  -onlyUsePackageVersionsFromResolvedFile \
  -disableAutomaticPackageResolution \
  build CODE_SIGNING_ALLOWED=NO IPHONEOS_DEPLOYMENT_TARGET=15.0
```

새 통합 테스트 타깃을 추가하면 실제 scheme과 simulator ID로 `xcodebuild test`를 실행하고 정확한 명령을 보고한다. 도구/권한 부족으로 못 실행했으면 성공으로 쓰지 않는다. 패키지 버전은 원래 고정 버전을 유지한다.

빌드 로그는 이번 작업 전용 경로로 남기고 파이프가 원래 종료 코드를 숨기지 않게 한다. 빌드와 설치/실행은 다른 검증이다. simulator 설치에 서명이 필요하면 해당 검증 명령만 조정하며 배포 식별자나 배포 설정을 임의로 바꾸지 않는다.

Orca 시뮬레이터 조작이 필요하면 해당 환경의 `orca-emulator` 스킬을 먼저 읽는다. 현재 안내 경로는 `/Users/somin/.agents/skills/orca-emulator/SKILL.md`다. 다른 환경에서는 사용 가능한 스킬/도구를 확인한다.

UI 증거에는 선택 날짜, 이관 합계/상세, 편집 후 합계, 재실행 후 같은 값, 저장 오류 후 열린 편집기를 포함한다. 합성 fixture를 사용하고 개인 기록을 스크린샷이나 저장소에 넣지 않는다.

## 15. 완료 조건과 최종 보고

- [ ] 원본 백업이 정규화/변환보다 먼저 완료된다.
- [ ] 이관 경로에서 구 화면 생성과 날짜 초기화가 원본을 변경하지 않는다.
- [ ] 모든 구 컬렉션/설정의 값과 순서가 목적 저장소에서 검산된다.
- [ ] 전체 데이터와 이관 완료 메타데이터가 한 번에 커밋된다.
- [ ] 중단/재실행/완료 후 재실행에서 중복과 덮어쓰기가 없다.
- [ ] 날짜별 조회·추가·수정·삭제가 저장소와 앱 재실행에서 유지된다.
- [ ] 과거 합계 전용 기록을 구분하고 하루 총량을 수정할 수 있다.
- [ ] 입력·파일 오류가 값을 잃거나 정상 0/빈 기록으로 보이지 않는다.
- [ ] 실제 Realm fixture 통합 검사와 시뮬레이터 실행 증거가 있다.
- [ ] 출시 전환/실사용 데이터/하위 OS 등 미검증 범위를 기록한다.

최종 보고에는 변경 파일과 동작, 실제 실행한 테스트/빌드 명령·종료 코드·로그 위치, 시뮬레이터 시나리오 결과, 데이터 보존 검산, 남은 차단 요인을 적는다. 기존 변경과 이번 변경을 구분한다. 커밋·push·배포를 완료 조건으로 삼지 않는다.

실제 배포 버전의 스키마와 사용자 데이터 표본을 확보하지 못해도 합성 fixture 기반 구현은 진행할 수 있다. 다만 그것만으로 기존 사용자 전체의 이관이 안전하다고 결론 내리지 않는다. 표현할 수 없는 원본이나 환경 제약이 생기면 해당 부분을 명시적으로 미완료로 남기고, 독립적으로 가능한 구현·검증은 마무리한다.

다음 후속 단계는 실제 출시 데이터 표본 검증과 지원 OS 결정, 날짜별 기록 UX 확정이다. 이후 Android 기술 검증과 공통 데이터 계약 적용, 통계/검색/즐겨찾기 리뉴얼, 마지막으로 AI 체험과 수익화 검증을 진행한다.
