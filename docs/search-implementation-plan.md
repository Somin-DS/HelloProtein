# 음식 검색 연결 구현 계획

작성일: 2026-10-07. 상태: **부분 구현(2026-10-07)** — 영어 로컬 카탈로그 검색(B1–B4)은 구현·검증했고, 한국어는 B0에서 서비스 종료가 확인돼 ‘사용 불가’ 상태로만 연결했다. 근거는 [공급자 검증](evidence/2026-10-07-search-provider/README.md)과 [실행 증거](evidence/2026-10-07-search/README.md). 대상: PR #8 이후 검색 B단계를 구현할 개발 에이전트. 작성: root, 본사 기획·그로스·디자인·마케팅·개발·QA·프롬프트 엔지니어 역할 공동 검토.

기존 사용자의 음식 검색을 새 SwiftUI 추가 화면에 연결한다. 영어 키워드 검색과 한국어 검색, 최근 검색, 검색 언어를 복원하고 검증된 기준량의 음식을 선택한 날짜에 기록한다. **데이터 출처와 기준량을 확인한 뒤 자동 기록을 허용하는 것**이 첫 번째 선행 조건이다. 구현 순서는 공급자 검증 → 도메인과 저장 계약 → 검색 공급자와 세션 → 화면 연결 → 회귀 검증이다.

## 기준과 선행 완료 사항

- 기준 main: [PR #8](https://github.com/Somin-DS/HelloProtein/pull/8) 머지 `6d613190538d51476abcbc1456bae2d33d6ee85d`. 즐겨찾기 변경 감지 후 목록 갱신 수정 `60a013e8a18bb71073b037769c1ce9b25bebfbfb`가 포함돼야 한다. 작성 시 로컬 HEAD는 이 수정 커밋이며 다음 구현자는 최신 main에서 시작한다.
- [전체 A와 B 계획](favorites-search-implementation-plan.md)의 B를 구체화한 문서다. A 구현 및 검증은 [즐겨찾기 실행 증거](evidence/2026-10-07-favorites/README.md), 이번 역할별 검토는 [공동 검토 기록](reviews/2026-10-07-search-team-review.md)을 참고한다. B의 세부 구현과 완료 판정은 이 문서를 따른다.
- A 완료: 직접 입력·즐겨찾기 2탭, 고정 대상 날짜, 즐겨찾기 관리·다중 추가, 기록과 선택적 즐겨찾기 동시 저장, dirty 전환 확인, 작업별 미확정 후처리. PR #8 후속 앱 테스트는 86개 통과했다.
- 기존 무료 검색과 즐겨찾기는 계속 무료다. 사용자 기록·ID·이관 원문·백업·이관 완료 증거를 보존한다. 현재 일반 iPhone UI를 기준으로 확장한다.
- 제품 코드, 빌드, 시뮬레이터 실행은 이번 문서 작성 범위가 아니다. Figma 원본과 공급자 공식 문서·실제 API 응답을 이번에 재검증하지 않았으므로 아래 B0가 미완료 상태다.

| 오류·취소·페이지·미확정·기준량 불명 처리 | 검색 추가와 즐겨찾기 저장을 동시에 하는 새 옵션 |

영어 또는 한국어 중 한 공급자만 검증돼 구현된 경우 해당 부분의 완료만 보고한다. 이름 복사 fallback만 제공하는 공급자는 검색 자동 기록 복원이 완료된 것으로 계산하지 않는다. 검증 실패 때문에 다른 순수 로직·fixture 테스트까지 중단할 필요는 없지만, 미검증 데이터를 자동 기록하거나 B 전체 완료로 보고하지 않는다.

## B0 공급자 검증

구현 시작 시 `docs/evidence/<실제 날짜>-search-provider/README.md`에 공급자별 증거표를 작성한다. 공식 원문 URL과 확인일, 키를 제거한 응답 fixture, 필드 매핑을 남긴다. 기존 문구의 ‘100g 기준’이나 그럴듯한 단백질 값은 근거가 아니다.

| 확인 항목 | 완료 증거 |
| --- | --- |
| 영어 파일 출처 | 원본 데이터셋·버전·행 대응 근거, 이용·재배포 조건, 필요한 출처 표기. 이름이 비슷하다는 이유로 다른 데이터셋의 설명을 적용하지 않는다. |
| 기준량 | 단백질 필드의 단위와 분모가 100g인지, 제품 1개인지, 제공량인지 공식 설명과 응답으로 확인. 기준량 필드의 단위도 함께 확인한다. |
| 식별자 | 공급자 식품 ID, 로컬 카탈로그 버전과 고정 행 ID 정책. 이름만으로 동명 항목을 합치지 않는다. |
| 한국어 API | 현재 사용 가능한 서비스 ID, 공식 HTTPS 주소, 인증 방식, 검색 파라미터, 오류코드, 빈 결과, 페이지 범위·총건수·제한을 확인한다. |
| 앱 인증 설정 | 키 없음·빈 문자열·치환되지 않은 빌드 변수 처리. 키를 저장소·로그·fixture·캡처에 노출하지 않는다. 키가 URL 경로에 들어가면 전체 URL을 오류에 출력하지 않는다. |
| 표본 응답 | 정상·0건·오류·페이지 끝·기준량 누락 응답을 익명화해서 계약 테스트에 사용. 숫자·단위 매핑은 대표 품목 몇 건을 수작업으로 대조한다. |

영어의 출처·재배포 근거를 찾지 못하면 해당 파일을 검증 완료로 취급하지 않는다. 한국어 서비스가 폐지됐거나 HTTPS·인증 조건을 충족하지 못하면 ATS 완화나 임의 서비스 교체로 우회하지 않는다. B0 증거와 대체 선택지의 범위·비용·데이터 차이를 문서화한다. 새 유료 공급자·계정·백엔드·라이선스 계약이 필요하면 그 선택만 사용자에게 확인하고, 독립적인 도메인·UI fixture 작업은 계속할 수 있다.

출처·이용 조건이 확인된 데이터라도 개별 행의 기준량이 불명확하면 그 행은 자동 추가 불가다. 데이터 사용 자체가 확인되지 않은 공급자와 단순히 한 행의 단위가 누락된 경우를 같은 것으로 취급하지 않는다.

## 검색 결과와 수량 계약

새 검색 결과 DTO는 공급자 응답 DTO와 분리한다. 필요한 필드는 `providerID`, 버전 또는 데이터 식별자, `itemID`, 음식명, 원문 단백질 값, 검증된 centigrams, 기준량과 단위, 표시 출처, 선택 가능 여부와 이유다. 구체 타입명은 변경 가능하나 확인 불가 상태를 0이나 임의 100g으로 대체하지 않는다.

- 로컬 항목 ID는 검증된 카탈로그 버전과 고정 행 위치 또는 명시적인 매핑으로 만든다. 매 검색 UUID 생성·이름 hash만 사용·정렬 후 index 사용을 금지한다. 카탈로그를 교체할 때 버전도 변경한다.
- 영어 검색은 trim 후 이름의 대소문자·발음부호를 무시한 부분 일치로 필터한다. 원래 카탈로그 순서를 유지한다. 빈 query는 전체 파일 반환 대신 최근 검색을 보여준다.
- 영어 JSON 숫자는 Decimal 또는 손실 없는 숫자 표현으로 디코드한다. `Double * 100`을 저장 계산 경로로 사용하지 않는다. g를 centigrams로 변환할 때 양수 절반 올림으로 반올림하고 변환 전후 범위·양수·overflow를 확인한다. 예: 1.005g → 101 centigrams, 0.004g → 0이므로 선택 불가. 반올림된 값은 화면에 알린다.
- 0·음수·숫자 아님·NaN·무한대·범위 초과는 선택 불가다. 기준량이 0·누락·지원되지 않는 단위인 경우도 구분해서 안내한다. 단위 환산이나 밀도 가정은 하지 않는다.
- 검증된 100g 기준 결과를 선택하면 `FoodQuantity(value: "100", unit: .gram)`과 해당 단백질을 저장한다. serving/piece는 실제 원천이 해당 단위를 정의할 때만 사용한다. ‘기준량 없음’을 serving 1로 바꾸지 않는다.
- 이번에는 결과에 표시된 기준량을 항목당 한 번 추가한다. 선택 순서를 기록 순서로 유지한다. 선택 해제·재선택은 같은 세션의 record ID를 유지하고, 새 검색 세대의 결과에는 새 ID를 배정한다.
- 공급자 정보는 검색 중 출처 표시에 사용한다. 영속 기록에는 기존 필드인 name/protein/quantity/source를 저장한다. 공급자 ID를 `legacySourceID`에 넣지 않는다. 저장 후 최신 공급자와 동기화하거나 값이 자동 갱신된다고 약속하지 않는다.
- 홈 기록 행과 기존 기록 편집 화면에서도 저장된 수량·단위를 시각적으로, VoiceOver로 읽을 수 있어야 한다. 검색 기록의 이름·단백질을 사용자가 수정하면 기존 `quantity`·`source`는 보존한다. 수정 값을 공급자 인증값으로 표현하지 않는다. 수량 자체를 수정하는 UI는 후속이다.

## 화면과 초안 정책

추가 시트를 열 때 정한 `target.day`를 검색에도 그대로 사용한다. 과거 날짜와 자정 이후에도 대상 날짜를 바꾸지 않는다. 검색 전용 전체 화면이나 새 홈 탭을 만들지 않는다.

```text
기록 홈 → 추가 시트
  직접 입력   검색   즐겨찾기
              대상 날짜
              음식 검색 언어
              검색창과 검색 실행
              실행한 검색어와 결과 언어
              최근 검색 또는 결과와 상태 안내
              선택 개수와 단백질 합계와 N개 추가
```

검색어 입력값 `queryDraft`와 결과 기준 `executedQuery`를 분리한다. 입력만 고쳤다는 이유로 기존 결과·선택을 숨기지 않는다. 새 검색 실행, 최근 행 재검색, 언어 변경 때 선택이 있으면 버리기 확인을 먼저 받는다. 취소하면 기존 결과·선택·확인된 언어가 유지되며 새 요청이나 저장이 시작되지 않는다.

탭 이동은 A의 현재 탭 dirty 확인 정책을 따른다. 검색에서는 음식 선택이 dirty이며 단순 검색어·결과·최근 목록 펼침만으로 버리기 확인을 요구하지 않는다. 확인 후 검색 탭을 떠나면 요청을 취소하고 검색 세션을 무효화한다. 재진입은 저장된 언어와 최근 검색을 기준으로 시작한다. 탭 간 혼합 장바구니는 없다.

| 화면 상태 | 동작 |
| --- | --- |
| 초기 또는 빈 query 실행 | 최근 검색. 공백 검색을 저장하거나 전체 카탈로그를 불러오지 않는다. |
| 검색 중 | 진행 표시와 취소 가능한 닫기·탭 이동. 네트워크 로딩과 저장 busy를 구분한다. |
| 결과 있음 | 음식명, 단백질, 기준량, 출처, 선택 상태. 긴 이름·단위는 줄바꿈한다. |
| 0건 | 다른 검색어 제안과 직접 입력 진입. 오류로 표현하지 않는다. |
| 요청 실패 | 원인에 맞는 문구와 재시도. 영어 파일 로드 실패를 네트워크 오류로 표현하지 않는다. |
| 공급자 사용 불가 | 키 누락·서비스 구성 미완료 안내와 직접 입력. 무한 로딩을 남기지 않는다. |
| 다음 페이지 실패 | 기존 결과와 선택 유지, 해당 페이지 재시도. 처음 검색 결과까지 지우지 않는다. |
| 선택 불가 행 | 행은 설명과 함께 보이되 추가 체크는 비활성. 기준량 불명과 0g을 구분한다. |
| 저장 pending | 결과 열람은 가능하나 입력·선택·탭·언어·이력 삭제·추가 등 변경 동작은 잠금. 재확인 및 기존 pending 닫기 정책만 허용한다. |

기준량을 확인할 수 없는 행의 ‘이름으로 직접 입력’은 특별한 전환이다. 선택이 있으면 버림 확인 후, 음식명만 직접 입력 초안에 복사한다. 단백질은 공란, 즐겨찾기 저장은 OFF, 대상 날짜는 유지한다. 취소 시 아무것도 변경하지 않는다. 일반 `applySwitch`가 복사된 값을 다시 지우지 않게 전환을 한 작업으로 처리한다. 직접 입력에 복사된 이름은 dirty로 취급한다.

일반 iPhone SE급 작은 폭과 큰 iPhone에서 검사한다. 검색 결과는 세로 스크롤, 선택바는 키보드·safe area를 피하고 접근성 글자에서는 세로 배치를 허용한다. 각 선택·삭제·언어·추가 컨트롤은 최소 44pt다. VoiceOver는 음식명·단백질·기준량·선택 여부·선택 불가 이유를 구분한다. 현재 라이트 테마를 유지하며 다크 모드 지원 완료라고 표기하지 않는다.

## 비동기 검색과 페이지 계약

`FoodSearchProvider`는 식품 조회만 담당한다. 로컬/원격 공급자를 주입할 수 있게 하고 실제 API 호출 없이도 fixture와 지연 응답으로 테스트할 수 있게 한다. 한국어 URL은 공식 계약에 맞춰 검색어를 안전하게 인코딩한다. 한글·공백·따옴표·슬래시·&·%를 포함한 검색어를 검사한다.

1. 명시적 검색 실행 직전에 query와 확인된 언어를 고정한다. 선택 버림 확인이 끝나기 전 기존 요청·결과는 유지한다.
2. 실행이 확정되면 이전 요청을 취소하고 새 request ID와 시트 세션 ID를 만든다. 검색어 이력 저장을 시작한다.
3. 이력 저장 callback에서 request ID, 세션 생존, 현재 탭을 다시 검사한다. 이미 닫혔거나 다른 검색으로 바뀌었으면 네트워크를 시작하지 않는다.
4. 이력 저장 성공·확정 실패·미확정 결과를 각각 처리한 뒤 유효한 요청만 공급자에 보낸다. 저장 실패가 검색 자체의 실패로 바뀌지 않게 한다.
5. 응답과 모든 오류 callback에도 request ID·언어·페이지 ID를 검사한다. 취소된 응답은 UI·선택·로딩 상태를 덮어쓰지 않는다. A 검색 후 B 검색의 결과가 먼저 온 역순 응답을 필수 테스트한다.
6. 닫기·탭 이탈·언어 변경은 관련 task를 취소하고 세대를 무효화한다. 저장 작업이 진행 중이면 기존 busy 정책 때문에 해당 동작을 먼저 차단한다.

네트워크 `isSearching`과 전역 저장 `isBusy`는 별도 상태다. 네트워크 응답 실패/timeout/취소/디코드 오류/API 오류/0건 모두 해당 요청의 로딩을 종료한다. 저장 busy를 네트워크 완료까지 끌고 가지 않는다.

한국어 페이지 크기·오프셋은 B0의 공식 계약으로 정한다. 최초 5개를 전체로 표현하지 않는다. `hasMore`는 검증된 응답 계약으로 판단하며 다음 페이지 동시 중복 요청을 막는다. 더 보기는 현재 결과의 연장이므로 최근 검색 쓰기를 반복하지 않는다. 동일 ID의 중복 페이지 행은 중복 표시하지 않고 선택 순서를 보존한다. 같은 ID의 내용이 달라지면 조용히 선택 값을 교체하지 말고 영향받은 선택을 해제하고 다시 확인하도록 안내한다.

실패한 동일 요청의 ‘다시 시도’는 네트워크 조회만 반복한다. 검색 버튼 재실행과 최근 검색 행 탭은 새로운 명시 검색이므로 이력을 처리한다. 이 차이를 테스트와 접근성 label에도 유지한다.

## 최근 검색과 검색 언어 저장

최근 검색은 기존 의미인 ‘사용자가 명시적으로 실행한 검색어’다. 음식 추가 성공 이력으로 의미를 바꾸지 않고 키 입력마다 저장하지 않는다. 공급자 오류나 0건이어도 실행한 검색어는 이력 저장 대상이다. 시간 정보가 없으므로 ‘몇 분 전’ 등은 표시하지 않는다. 최근 행 재검색은 현재 확인된 검색 언어를 사용한다.

- 조회는 position 순서다. 조회만으로 순서·원문·ID를 변경하지 않는다. 오래된 항목을 개수 제한으로 삭제하지 않고 더 보기 또는 스크롤로 전체 접근을 제공한다.
- 새 query는 trim 후 공백만이면 거부한다. 기존 항목의 trim 결과와 정확히 같은 항목 중 position이 가장 앞선 하나를 재사용하고 맨 앞으로 이동한다. 그 항목의 저장 value 원문·id·legacySourceID를 유지한다. 다른 중복은 삭제하지 않는다. 대소문자·동의어 병합은 하지 않는다.
- 재검색 이동이나 신규 삽입 시 나머지 안정 순서를 유지한 채 0부터 연속 position을 같은 modify에서 부여한다. 새 항목은 trim한 query를 저장한다. 신규 ID는 해당 이력 저장 시도와 미반영 재시도 동안 고정한다.
- 이력 삭제는 확인 후 해당 ID만 제거한다. 기존 음식·즐겨찾기는 유지한다. 빈 기존 검색어는 표시용 대체 문구, 재검색 비활성, 명시적 삭제를 제공한다.
- 앱 UI 언어와 음식 검색 언어를 구별한다. 초기값은 확인된 `state.settings.searchLanguage.resolved`다. 레거시 UserDefaults로 되돌아가지 않는다.
- 검색 언어 변경은 별도 저장 작업이다. 새 선택은 위 interpret가 해석하는 raw 문자열로 저장한다. 조회만으로 알 수 없는 원문을 교정하지 않는다. 이미 확인된 언어를 다시 선택하면 불필요한 쓰기를 하지 않는다.
- 언어 변경 성공 후에만 표시 언어·공급자를 바꾸고 이전 결과·선택을 비운다. queryDraft는 유지하고 명시적 검색 실행을 기다린다. 선택 버리기 동의는 언어 저장 성공 시 폐기에 대한 동의다. 반영이 확인되기 전까지 이전 결과·선택 스냅샷·record ID·queryDraft를 보관한다. 요청 취소·세대 무효화가 이 스냅샷을 지우지는 않는다. 저장 실패나 재확인 미반영이면 이전 언어·결과·선택을 유지하고 오류를 알린다. pending이면 확인 전까지 이전 언어로 표시하고 잠근다.

## 저장 작업과 미확정 결과

`RecordHomeViewModel`의 단일 저장 경로를 사용한다. 런타임 작업 종류에 `searchBatch`, `searchHistory`, `searchHistoryDelete`, `searchLanguage`에 해당하는 구분을 추가하고 기존 `AddSheetPolicy.afterConfirmed`와 홈 안내를 갱신한다. 이름은 조정할 수 있으나 용도를 합치지 않는다. schema나 pending 영속 필드는 추가하지 않는다.

| 작업 | 정상 성공 또는 재확인 반영됨 | 교체 전 실패 또는 재확인 미반영 | 재확인 읽기 실패 |
| --- | --- | --- | --- |
| 검색 결과 N개 추가 | 최신 기록 반영 후 시트 닫기 | 선택·대상 날짜·record ID 유지, 명시적 재시도 | 잠금 유지, 성공/실패 단정 금지 |
| 검색어 저장 | 최신 최근 검색 반영, 시트 유지 | 이력 미저장 안내, 결과 열람 허용. 자동 이력 재저장 금지 | 잠금 유지, 이미 도착한 결과 열람만 가능 |
| 검색어 삭제 | 목록 갱신, 시트 유지 | 해당 행 유지·명시적 재삭제 가능 | 잠금 유지 |
| 검색 언어 변경 | 확인된 언어 적용, 결과 초기화, 시트 유지 | 이전 언어 유지, 명시적 변경 재시도 | 이전 확인 언어 표시, 잠금 유지 |

검색어 저장의 최초 callback은 pending이어도 현재 유효한 검색 요청 한 번을 시작할 수 있다. **재확인 callback에서는 검색도 이력 쓰기도 다시 시작하지 않는다.** `notApplied`이면 결과를 음식 기록에 추가하는 것은 잠금 해제 뒤 가능하지만, 검색어 이력을 자동으로 되살리지 않는다. 닫은 시트의 pending은 홈 재확인으로 상태만 갱신하고 시트·검색 요청을 재생성하지 않는다.

검색 batch는 검증된 선택 스냅샷·고정 target.day·고정 record ID로 FoodRecord(source: .search, quantity: 검증된 기준량)를 구성하고 단일 modify에서 N개 전부 저장하거나 0개다. 최신 일일 합계와 모든 ID·단백질·수량·checked sum을 검사한다. 즐겨찾기 목록 대조를 요구하는 `FavoriteBatch`를 그대로 검색용으로 호출하지 말고 검증된 검색 전용 batch 또는 작은 공통 기록 helper를 사용한다. 이력 저장을 음식 추가 transaction에 중복해서 넣지 않는다.

오류가 나도 자동으로 단백질을 고치거나 일부만 추가하지 않는다. PR #8의 최신 즐겨찾기 목록 갱신과 재선택 회귀 테스트를 유지한다. 검색 결과는 immutable snapshot을 쓰며 저장 직전 공급자 재조회로 사용자가 본 값을 조용히 바꾸지 않는다.

## 구현과 PR 순서

1. **B0 근거 확정:** 최신 main과 PR #8 수정 포함 여부 확인. 공급자 증거표·샘플·필드 매핑·허용 단위·페이지 규칙·미해결 사항을 작성한다. 공급자 변경이 필요하면 근거를 갖춘 선택지로 좁힌다.
2. **B1 도메인과 쓰기:** 이력 helper·언어 명령·검색 batch·작업 종류와 pending 정책을 구현하고 순수/VM 테스트로 고정한다. 아직 작동하지 않는 검색 탭을 노출하지 않는다.
3. **B2 공급자와 세션:** 검증된 adapter, Decimal 매핑, 취소·세대 검사·페이지·오류 상태를 연결하고 deterministic fixture 테스트를 통과시킨다.
4. **B3 화면:** 검색 탭·최근 검색·언어·선택바·fallback·수량 표시를 연결한다. 기존 직접 입력/즐겨찾기 흐름과 공통 버림·잠금을 재사용한다.
5. **B4 통합 검증:** 아래 표의 테스트와 일반 iPhone 캡처, Debug/Release 검증을 수행한다. 공식 서비스 실연결 smoke와 fixture 테스트를 구분해 보고한다.
6. **리뷰:** PR 본문에 B0 증거, 지원 공급자, 실제 완료 범위, 검증 결과·미검증·키 구성 조건을 기재한다. 이 문서 작성 요청 자체는 구현·PR 생성·머지 지시가 아니다.

기본 산출은 A와 분리된 검색 B PR 하나다. 변경이 커져 분리할 경우 B0/B1 기반 PR → B2/B3/B4 사용자 기능 PR 순서로 나누며, 기반 PR 병합을 검색 기능 완료로 표현하지 않는다. 공급자 검증이 미완료면 검증된 일부만 담은 PR의 범위를 제목·본문에 명시한다.

실제 파일의 afterReplace 실패와 DEBUG 대역의 notApplied/readFailure는 구분해서 증거를 남긴다. 실 API 장애를 일부러 만들 필요는 없고 URLProtocol 등 공급자 대역으로 결정적으로 검증한다. 실제 API smoke는 B0의 허용된 접근 조건에서 최소 정상·0건·페이지를 확인한다.

대표 사용자 흐름인 ‘검색 → 기준량 확인 → 고정 날짜 기록 완료’의 성공 여부와 수동 입력으로 우회한 이유를 B4 증거에 기록한다. 새 계측 SDK를 도입하거나 리텐션·구독 전환율 개선을 검증 없이 주장하지 않는다.

실행 명령은 현재 프로젝트 scheme과 설치된 simulator UDID를 확인한 뒤 사용한다. 기존 임시 UDID를 보편적인 기기 ID로 복사하지 않는다.

```sh
swift test --package-path HelloProteinCore --scratch-path /private/tmp/hp-search-core
swift test --package-path MigrationCore --scratch-path /private/tmp/hp-search-migration
xcodebuild -project ProteinTracker/ProteinTracker.xcodeproj -scheme ProteinTracker \
  -destination 'platform=iOS Simulator,id=<확인한 UDID>' \
  -derivedDataPath /private/tmp/hp-search-build \
  -onlyUsePackageVersionsFromResolvedFile test CODE_SIGNING_ALLOWED=NO
xcodebuild -project ProteinTracker/ProteinTracker.xcodeproj -scheme ProteinTracker \
  -configuration Release -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /private/tmp/hp-search-release \
  -onlyUsePackageVersionsFromResolvedFile build CODE_SIGNING_ALLOWED=NO
```

로그·xcresult·일반 iPhone 캡처는 실행 날짜별 evidence에 연결한다. Release에서 DEBUG 실패 주입·fixture 코드가 제외되는지 기존 방식으로 확인한다. 테스트 개수는 실제 결과를 기입하고 이전 86개를 그대로 성공 결과로 복사하지 않는다.

## 완료 조건과 인계

- [ ] 영어·한국어 각각 출처·이용 조건·기준량·ID·정밀도·오류·페이지 계약과 키 없는 동작이 근거로 확정돼 있다.
- [ ] 검증된 결과만 선택 가능하며, 표시된 기준량의 기록 N개가 고정 날짜에 한 번씩 추가된다.
- [ ] 최근 검색·언어·음식 추가의 저장 목적과 pending 후처리가 분리돼 있다.
- [ ] 취소·지연 callback·역순 응답·언어 변경·더 보기로 잘못된 결과나 중복 기록이 생기지 않는다.
- [ ] 기존 원문·ID·무료 기능·schema·이관·미확정 계약을 보존한다.
- [ ] 단위/VM/공급자/일반 iPhone UI 검사와 한영 문구 검토 결과가 기록돼 있다.
- [ ] 미검증 공급자·실기기·최소 OS·접근성 항목을 숨기지 않으며, fallback만 구현한 상태를 B 전체 완료라고 하지 않는다.
