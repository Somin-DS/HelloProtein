## 1. 결론

이관·저장·SwiftUI 연결이라는 이전 계획의 주요 구현이 들어왔다. 전체 상태를 하나의 파일로 저장하고, 기존 storyboard 자동 생성을 제거하고, 날짜별 편집 결과를 영속화한 방향은 적절하다.

다만 **복구 증거의 읽기 오류를 무시하는 문제와 파일 교체 후 오류를 일반 저장 실패로 처리하는 문제를 수정하기 전에는 병합 승인을 권하지 않는다.** 두 문제 모두 정상 흐름 테스트가 통과해도 남는 데이터 안전성 결함이다.

새 흐름은 아직 개발용 진입 기능이다. 목표 설정·검색·즐겨찾기 사용 경로가 없으므로, 이번 PR을 병합하더라도 사용자 대상 기본 활성화나 출시 준비 완료로 해석하면 안 된다.

## 2. 리뷰 지적

### R1 — P1: 복구 증거 읽기 실패를 ‘증거 없음’으로 처리한다

위치: `MigrationCore/Sources/MigrationCore/MigrationCoordinator.swift:173-194`.

`completionEvidence()`의 오류를 `try?`로 지우고, `backupExists`도 백업 디코딩 오류를 false로 바꾼다. 다음 상황에서 문제가 발생한다.

1. 이관 완료 후 사용자가 새 저장소에서 기록을 추가/수정한다.
2. `app-state.json`이 없어지고 `migration-completed.json`은 손상되거나 읽을 수 없는 상태다.
3. 파일 존재를 보는 시작 정책은 새 흐름으로 보낸다.
4. 조정자는 완료 증거의 읽기 오류를 무시한다.
5. 구 원본이 있으면 예전 데이터를 다시 이관하고, 원본/읽을 수 있는 백업이 없으면 빈 신규 저장소를 만든다.

이미 알려진 데이터 손실 상태를 정상 초기화로 덮어버린다. 새 기록은 구 Realm에 없으므로 자동 재이관도 안전한 복구가 아니다. 손상된 백업만 남았을 때도 같은 종류의 문제가 생긴다.

요구 수정:

- 증거를 `missing / valid / corrupt / unreadable / unsupported`로 구분한다.
- 오직 실제 missing만 다음 초기화 판단으로 진행한다.
- 완료 증거 또는 유일한 백업을 읽지 못하면 복구 상태로 멈추고 모든 파일을 보존한다.
- `recordCompletionIfMissing`도 손상된 증거를 자동 덮어쓰지 않도록 정책을 명시한다. 정상 저장소가 있을 때 보조 증거 재생성 여부는 별도의 검증된 수리 동작이어야 한다.

### R2 — P1: 파일 교체 후 실패가 재시도 시 중복 저장으로 이어진다

위치:

- `HelloProteinCore/Sources/HelloProteinCore/AppStateStore.swift:249-259`
- `ProteinTracker/ProteinTracker/Renewal/RecordHomeViewModel.swift:106-110,159-181`

`rename`이 성공한 시점에는 새 상태가 이미 최종 파일에 들어갔다. 이후 최종 파일 읽기/검증이 실패하면 저장소는 일반 오류를 던진다. ViewModel은 화면의 이전 상태를 유지하고 편집 시트를 열어두며, 추가 버튼의 재시도는 새 UUID를 만든다.

재현 조건: 새 음식 추가 → rename 성공 → 최종 read-back 접근 실패 → 저장 실패 안내 → 접근 복구 → 사용자가 저장 재시도. 첫 음식은 이미 파일에 있으므로 두 번째 UUID로 동일 음식이 추가된다. 삭제에서도 디스크에서는 삭제됐는데 화면에 남아 다음 시도에서 notFound가 발생할 수 있다.

요구 수정:

- 교체 전 실패와 교체 후 결과 확인 불가를 저장 API에서 구분한다.
- 교체 후 상태가 불명확하면 일반 재저장 대신 읽기 재확인을 수행한다.
- 한 편집 작업의 operation ID와 추가 record ID를 재시도 동안 유지한다.
- 읽을 수 있을 때 같은 작업의 반영 여부를 확인하고 성공으로 수렴한다. 확인할 수 없으면 쓰기를 막고 입력을 유지한다.
- 이미 교체된 파일을 이전 파일로 자동 되돌리지 않는다. 뒤에 성공한 변경까지 잃을 수 있다.
- ‘어떤 실패든 이전 파일이 그대로’라는 저장소 주석을 실제 커밋 경계에 맞게 수정한다.

## 3. 차단 지적과 구분할 후속 항목

다음 항목은 위 두 결함과 같은 확정적 병합 차단 사유로 취급하지 않는다. 다음 제품 단계 또는 출시 검증에 포함한다.

- 새 흐름에서 목표 미설정/확인 필요 상태를 보여주지만 목표를 설정하는 동작은 없다.
- 즐겨찾기·검색 이력은 저장됐지만 새 화면에서 활용할 수 없다. 기존 UIKit으로 되돌아가 데이터를 쓰는 우회 연결은 금지한다.
- 세 개의 sheet 상태는 하나의 편집 라우트로 정리할 수 있다. 현재 코드만으로 실제 표시 실패를 단정하지 않는다.
- 저장 중 swipe dismiss는 막지만 취소 버튼은 활성 상태다. 저장 진행 중에는 취소를 비활성화하거나 취소 의미를 명확히 한다.
- 앱이 계속 foreground인 채 자정을 넘는 상황의 오늘 표시와 시간대 변경 반영을 추가 확인한다. 현재 갱신은 active 전환/오늘 선택에 의존한다.
- 백업 Date 직렬화는 ISO 문자열을 사용한다. 원본 전체 정밀도 보존을 요구한다면 소수 초가 있는 실제 값으로 round trip과 지문 안정성을 확인한다.
- 실제 출시 Realm 스키마, 실사용 데이터, iOS 13/14, 실기기는 검증되지 않았다. 기능 플래그 유지 상태와 출시 가능 상태를 분리한다.
- 디렉터리 fsync와 전원 차단 내구성은 PR에서 이미 제한으로 보고했다. 이번 리뷰의 SIGKILL/파일 오류 검증과 구분한다.

## 4. 검증 기록

이번 리뷰에서 실행:

```sh
swift test --package-path HelloProteinCore --scratch-path /private/tmp/helloprotein-pr2-core-review
swift test --package-path MigrationCore --scratch-path /private/tmp/helloprotein-pr2-migration-review
```

결과: 각각 40개/53개 통과, 모두 exit 0. 기존 테스트는 위 R1/R2의 정확한 실패 조합을 검증하지 않는다.

추가 재현용 코드는 작업 폴더 밖 `/private/tmp/helloprotein-pr2-review`에 격리했다. 제품 파일을 변경하지 않고 현재 두 패키지를 경로 의존성으로 사용한다. 실행 로그는 `/private/tmp/helloprotein-pr2-review.log`다. 임시 디렉터리는 다른 환경으로 전달되지 않으므로 아래 재현 절차를 정식 회귀 테스트로 옮긴다.

`swift test --package-path /private/tmp/helloprotein-pr2-review` 실행 결과: 재현 테스트 2개 통과, exit 0. 여기서 통과는 **R1의 빈 저장소 생성과 R2의 중복 저장이 실제로 발생했음을 확인했다는 뜻**이다. 수정 후 정상 동작을 확인한 결과가 아니다. 최초 실행은 샌드박스의 Swift 모듈 캐시 쓰기 제한으로 실패했고, 승인된 재실행에서 위 결과를 얻었다.

재현 절차:

- R1: 임시 evidence 디렉터리에 잘못된 JSON의 completion 파일만 생성하고, 새 저장소와 구 원본 없이 조정자를 실행한다. 현재 동작은 freshInstall이다. 수정 후에는 recovery와 목적 파일 미생성을 기대한다.
- R2: 정상 초기 저장소를 만든다. `afterReplace` hook에서 최종 파일 권한을 읽기 불가로 바꿔 실제 최종 디코딩을 실패시킨다. modify가 throw한 뒤 권한을 되돌리고 읽으면 첫 추가가 남는다. 새 ID로 재시도하면 두 행이 된다. 수정 후 같은 작업을 재시도해도 한 행이어야 한다. 권한 재현은 비-root 환경에서 실행한다.

이번 리뷰에서는 iOS 빌드·iOS 통합 테스트·시뮬레이터 UI를 재실행하지 않았다. PR의 25개 iOS 테스트 및 화면 증거는 작성자의 보고이며 이번 독립 검증 결과와 구분한다.

## 6. 구현 순서

### 단계 A. 회귀 테스트를 먼저 추가

현재 실패를 적색 테스트로 고정한다. 임시 재현 코드는 현재의 잘못된 동작이 발생함을 확인하는 용도이므로, 정식 테스트는 **수정 후 기대 동작**을 assert해야 한다.

| 테스트 | 기대 계약 |
| --- | --- |
| 목적 파일 없음 + 손상 completion + 구 원본 없음 | recovery, 목적 파일 미생성, 증거 불변 |
| 목적 파일 없음 + 읽기 불가 completion + 구 원본 있음 | 재이관 안 함, 구 원본/capture 호출 안 함 |
| 목적 파일 없음 + 손상된 유일 백업 | 신규 설치 생성 금지 |
| 모든 파일/원본 실제로 없음 | 신규 설치 정상 생성 |
| 정상 완료 저장소 + 증거 손상 | 정상 기록 보존, 명시된 보조 증거 정책 적용 |
| rename 이전 실패 | 디스크/화면 모두 이전 값 |
| rename 이후 최종 읽기 실패 | 결과 미확정, 추가 쓰기 차단 |
| 접근 복구 후 동일 추가 재시도 | 한 행, 한 번 증가한 합계 |
| 결과 미확정 후 앱 재실행 | 커밋된 기록 한 번만 표시 |
| 삭제/수정의 결과 미확정 | 성공 여부 재확인, 모순된 재시도 없음 |

기존 정수/날짜/이관 개수 검산 테스트를 유지한다. 테스트는 독립 URL/UserDefaults suite를 사용하고 실제 앱 데이터를 건드리지 않는다.

### 단계 B. 증거 읽기 계약 수정

대상: `MigrationCoordinator.swift`, `FileMigrationEvidenceStore`, 관련 테스트.

- 파일 존재와 디코딩 결과를 분리한다. Optional nil은 실제 파일 부재만 뜻하게 한다.
- `try?`로 무시한 I/O/디코딩 오류를 typed recovery로 전달한다.
- 완료 파일이 존재하지만 검증할 수 없으면 구 데이터 읽기·매핑·새 저장까지 진행하지 않는다.
- 백업의 존재 여부와 사용 가능한지 여부를 구분한다. UI의 backupAvailable도 손상된 파일의 존재만으로 true라 하지 않는다.
- 지원하지 않는 evidence/capture 버전은 명시적으로 멈춘다. 기존 포맷을 읽는 경로와 필요한 버전 필드를 정의한다.
- 목적 저장소가 정상일 때 보조 증거 오류는 사용자 기록을 차단해야 하는지 별도 정책으로 정한다. 핵심 조건은 목적 저장소를 재생성하거나 덮어쓰지 않는 것이다.

통과 기준: 단계 A의 증거 관련 테스트 통과, 오류 상태에서 원본·증거 바이트가 변경되지 않음.

### 단계 C. 커밋 결과와 멱등 재시도

대상: `AppStateStore.swift`, 필요한 `AppState` 메타데이터, ViewModel 테스트용 저장소.

권장 결과 계약:

```text
notCommitted(error)       교체 이전 실패: 안전하게 같은 작업 재시도 가능
committed(state)          최종 상태 확인 완료
indeterminate(operation)  교체는 됐으나 확인 불가: 읽기 재확인부터 수행
```

구체적인 enum/throw 방식은 코드에 맞게 정하되 위 세 의미를 혼합하지 않는다.

- 한 번의 사용자 저장 시도에 안정적인 operation ID를 부여한다. 새 음식 record ID도 시트의 편집 세션 동안 유지한다.
- 반영 확인은 이름/단백질 값 비교만으로 하지 않는다. 같은 음식을 두 번 먹는 정상 입력과 재시도를 구분해야 한다.
- 다시 읽은 저장소에 해당 작업이 확인되면 성공 처리한다. 다른 내용으로 같은 ID를 덮어쓰기보다 충돌을 명시한다.
- 확인 불가 동안 새 modify 요청을 막는다. 정상 데이터가 확인된 뒤에만 쓰기를 재개한다.
- 저장 API가 반환한 결과에 맞게 저장소 주석/오류 타입을 수정한다.
- operation 메타데이터를 저장할 경우 schema 2 기존 파일의 디코딩 호환성과 정리 정책을 테스트한다. 값이 없는 구 파일은 안전한 기본값으로 읽되 사용자 기록을 바꾸지 않는다.

통과 기준: 정상적인 별개 추가는 각각 저장되고, 동일 작업 재시도만 중복 없이 수렴한다. 교체 후 자동 rollback은 하지 않는다.

### 단계 D. 화면 상태 연결

대상: `RecordHomeViewModel.swift`, `RecordHomePrototypeView.swift`, 영어/한국어 문자열.

- 저장 중에는 저장·삭제·취소의 중복 실행을 막는다. 사용자가 화면을 닫았는데 뒤에서 저장되는 동작을 피한다.
- 교체 전 실패: 입력 유지, 실패 안내, 같은 작업 ID로 재시도.
- 결과 미확정: ‘저장 결과 확인 중’ 상태, 입력 유지, 일반 저장 버튼 비활성화, 재확인 동작 제공.
- 커밋 확인: 최신 저장소 상태를 반영하고 시트를 닫는다.
- 화면에서 날짜 이동이 있어도 편집 대상 날짜는 유지한다.
- 접근 복구 후 읽기 재확인 실패를 무한 자동 재시도하지 않는다. 사용자가 재시도할 수 있는 명확한 상태로 남긴다.

통과 기준: 저장 성공/실패/미확정 모두 디스크와 화면의 관계를 설명할 수 있고, 저장 후 재실행에서 중복이 없다.

### 단계 E. 통합 검증과 보고

1. 코어 두 패키지 테스트.
2. iOS 테스트 타깃의 이관·ViewModel 테스트.
3. Debug/Release 빌드에서 파일 오류 주입 기능의 포함 범위 확인.
4. 합성 데이터로 시뮬레이터 정상 이관과 날짜별 편집 회귀 확인.
5. 손상 completion 복구 화면 및 파일 보존 확인.
6. rename 후 읽기 실패 → 접근 복구 → 재확인 → 재실행에서 음식 한 행 확인.

시뮬레이터 오류 주입은 DEBUG 전용이어야 하며, 테스트 종료 시 자신이 변경한 fixture 권한을 복구한다. 실제 사용자 저장소를 chmod하거나 삭제하지 않는다. iOS UI 조작 시 환경의 simulator 스킬 지침을 따른다.

## 8. 그다음 제품 작업 순서

안전성 수정이 통과한 다음 별도 작업으로 진행한다. 다음 구현 에이전트가 아래까지 자동으로 범위를 확장하지 않는다.

1. **목표 설정/수정**: 신규 사용자의 목표 입력, 기존 잘못된 목표 확인, 적용일 기준 이력, 같은 날짜 변경 교체. 과거 목표를 현재 값으로 추정하지 않는다.
2. **즐겨찾기 조회·추가 입력**: 이관된 즐겨찾기를 새 저장소에서 표시하고 선택 날짜에 음식으로 추가. 기존 사용자의 무제한 즐겨찾기를 제한하지 않는다. 잘못된 레거시 값은 수정 안내 후 사용한다.
3. **검색 및 설정 연결**: 기존 UIKit의 Realm/UserDefaults 직접 접근을 저장소/서비스 경계로 옮긴다. 복귀 후 구 저장소에 쓰는 경로를 만들지 않는다.
4. **출시 이관 검증**: 실제 배포 스키마와 익명화 표본, 지원 OS 분포, 실기기 업그레이드, 실패 복구 정책을 확인한 뒤 기본 활성화를 판단한다.
5. **Android 기술 검증**: 날짜·정수 단위·목표 이력·레거시 합계 계약을 공통 fixture로 고정한 뒤 UI/저장 기술을 결정한다.
