# 기록 홈 UI 적용을 위한 다음 작업 계획

작성일: 2026-09-30. 대상: 다음 작업을 인계받는 구현 에이전트.

상태: 본사 역할별 문서·소스 검토 반영안. 제품 디자인 승인·구현·실행 검증은 별개다. 실제 참여 역할, 의견 조정과 검토 한계는 [공동 검토 기록](reviews/2026-09-30-ui-phase1-team-review.md)에 남긴다.

## 구현 진행 기록 — 2026-10-01

사용자의 “이건 그럼 너가 직접 작업해줘” 요청에 따라 `feat/renewal-home-phase1`에서 권장안을 직접 구현했다. 이번 적용 기준은 단일 추가 버튼, 크림 배경·민트 보조색·진한 녹색 주요 동작, Binggrae 숫자/시스템 본문, Renewal 전용 라이트 테마다. 이는 개별 디자인 항목에 대한 별도 시각 승인이나 최종 A/B 선택을 받았다는 기록은 아니다.

날짜·요약·음식 행·레거시 합계 컴포넌트와 테마를 분리하고 기존 편집 시트를 정리했다. 미확정 초안 미보존 안내와 잘못된 미반영 안내를 수정했다. 저장·이관·VM·schema·기본 실행 경로는 변경하지 않았다. 최신 실행 증거와 미검증은 [구현 검증 기록](evidence/2026-09-30-ui-phase1/README.md)을 기준으로 한다. 아래 체크리스트는 전체 검증을 통과한 것으로 일괄 체크하지 않는다.

## 목표와 현재 상태

다음 작업은 **검토된 UI 시안의 핵심 결정을 사용자와 정리하고, 확정한 디자인을 기존 SwiftUI 기록 홈에 적용하는 것**이다. 저장·이관 기능을 다시 만드는 작업이 아니다.

PR #4는 시안·명세·backlog를 포함해 병합됐다. 병합 커밋은 `d6ad3dd0f42643bc53c4814cdd037ea65d5c59dd`, 마지막 수정 커밋은 `e42af5a3da0dfd1576c0ca44dc1aa0bb324b63ca`다. 현재 로컬 브랜치는 병합 전 작업 브랜치에 머물 수 있으므로 시작 시 최신 main과 작업 상태를 확인한다. 기존 변경을 덮어쓰지 않는다.

병합은 문서와 시안의 기술 검토 완료를 뜻한다. **이번 홈·추가 배치, 브랜드 적용 범위, 다크 모드 지원은 아직 사용자 확정 사항이 아니다.** 이 문서 작성 요청도 제품 화면 교체 승인을 뜻하지 않는다.

현재 기반:

- 기존 Realm/UserDefaults 이관과 새 파일 저장소가 구현돼 있다.
- 날짜별 조회·추가·수정·삭제·과거 총량 편집이 동작한다.
- 저장 실패와 결과 미확정 상태를 구분하고 재확인한다.
- 새 화면은 임시 시스템 스타일을 사용한다. 목표가 있는 날짜에는 이미 `ProgressView`가 있다.
- 목표 편집·검색·즐겨찾기·히스토리·설정은 새 저장소를 사용하는 제품 화면으로 아직 연결되지 않았다.

해석 순서는 사용자 최신 결정 → 이번 plan의 범위·예외 → 해당 범위의 UI 명세 → backlog·HTML 참고다. 실제 소스는 현재 구현 사실의 근거이며 원하는 UX의 승인 근거는 아니다.

이 문서는 위 backlog의 첫 구현 분량을 구체화한다. 다음 사항은 이 문서의 지침을 적용한다.

1. 기존 backlog의 ‘현재 선형 막대 없음’은 실제 코드와 다르다. 현재 `goalState == .goal`에 있는 막대를 재사용해 스타일을 바꾼다.
2. 전역 `AccentColor`나 기존 색상 자산을 바꾸면 UIKit에도 영향이 갈 수 있다. 새 테마를 Renewal 화면 계층에만 적용한다.
3. 연결할 화면이 없는 히스토리·설정·목표 버튼을 제품에 먼저 노출하지 않는다. 시안에 있는 버튼이라는 이유만으로 비활성 가짜 메뉴를 만들지 않는다.
4. HTML은 시각·동작 참고 자료다. 각본형 저장, 자동 입력값, JS 수치 계산을 제품 로직으로 옮기지 않는다.
5. 시안 전체와 실제 앱 시더는 모든 날짜·상태가 동일하지 않다. 각 검증 fixture의 구체적인 입력과 기대값을 명시한다.

Figma는 PR #4 작성 시 직접 재확인하지 못했다. 기존 검토 기록을 근거로 삼은 부분과 새 제안을 구분한다. 이번 첫 구현을 Figma 원본과 완전히 일치하는 결과라고 보고하지 않는다.

## 먼저 확정할 디자인 결정

구현 에이전트는 기존 시안을 열어 다음 세 항목을 한 번에 검토할 수 있게 제시한다. 새 시안을 처음부터 다시 제작할 필요는 없다. 앞선 대화에서 이미 결정한 항목이 생겼다면 기록을 반영하고 같은 질문을 반복하지 않는다.

| 결정 | 권장안과 영향 | 현재 상태 |
| --- | --- | --- |
| 이번 홈과 추가 배치 | 날짜·요약·목록과 동작하는 단일 추가 버튼. 시안에서 이번 적용 영역과 후속 메뉴를 구분해 제시 | 미확정 |
| 브랜드 적용 | 크림·민트·기존 그린 유지, 주요 동작은 진한 녹색, 본문 시스템 서체, 섭취량 숫자에 Binggrae | 미확정 |
| 테마 범위 | 첫 적용은 라이트 우선 권장. 라이트만 선택하면 Renewal 루트에만 명시적으로 적용. 다크 선택 시 오류/시트까지 함께 검증 | 미확정 |

결정 기록에는 선택값, 사용자 확인일, 이번 PR 적용 범위, 후속 범위를 남긴다. 답변이 없으면 권장안을 승인으로 간주하지 않는다. 사용자가 UI 변화의 근거를 확인한 맥락에 따라 이번에 실제 바뀔 화면만 확인받는다. 최종 A/B 내비게이션은 후속 화면 연결 전에 결정하며 이번 착수 조건에서 제외한다. 기존 시안 전체를 승인 대상으로 오인하지 않도록 적용 영역을 표시한 비교 화면을 준비한다. 기존 backlog의 광범위한 결정 조건은 이번 공동 검토로 범위를 좁혔다.

확정 전에도 소스 조사, 상태 목록 정리, 현재 화면 캡처, 구현 diff 범위 산정은 수행할 수 있다. 제품 화면 변경은 확정 후 진행한다.

## 구현 순서와 작업별 완료 조건

### 1 기준 화면과 기능을 확보

최신 main을 기준으로 별도 작업 브랜치를 준비하고 기존 사용자 변경을 보존한다. 현재 앱의 오늘·과거 상세·과거 합계 전용·미확정 시트 화면을 합성 데이터로 캡처한다.

기존 UI를 비교하려면 별도의 신규 설치용 시뮬레이터 데이터 영역을 쓴다. 이관 완료된 설치에서 플래그를 지우고 구 경로로 강제 복귀하지 않는다. 플래그가 없어도 완료 증거가 있으면 새 흐름으로 가는 현재 정책을 유지한다.

완료 조건: 같은 데이터로 전후를 비교할 수 있고, 새 흐름과 구 흐름의 검증 환경이 구분돼 있다.

### 2 테마를 화면 범위에 적용

확정한 토큰을 Renewal 네임스페이스에 둔다. 새 색상 자산을 추가할 경우 기존 이름을 덮어쓰지 않는다. 시스템 전체 appearance나 전역 accent 설정으로 구 UIKit을 바꾸지 않는다.

숫자용 Binggrae 파일과 실제 PostScript 이름을 확인하고 Dynamic Type에 맞춰 비례 확대한다. 웹 시안의 Fredoka는 대체 서체이므로 앱에 새로 도입하지 않는다. 본문·보조 문구는 시스템 텍스트 스타일을 쓴다.

다크 미지원 결정이면 Renewal의 시트와 달력도 일관된 라이트 테마가 되는지 확인한다. 다크 지원 결정이면 색상 의미별 대응을 적용하고 혼합된 라이트 배경/흰 글자 조합이 없는지 검증한다.

브랜드의 연한 녹색을 기록 여부·진행 상태의 유일한 표식으로 쓰지 않는다. 기록 표식은 진한 색과 형태를 함께 사용하고 경고 아이콘에는 어두운 기호와 문구를 둔다. 색상값 대비 계산은 실제 렌더 검증을 대체하지 않는다. Figma 임시 와이어프레임은 색·서체의 승인 근거가 아니다.

완료 조건: 새 흐름에만 디자인이 적용되고 글자 확대·테마 전환에서 읽을 수 있다.

### 3 컴포넌트를 추출하며 상태 수명을 보존

화면을 날짜 줄·요약·목록·이전 합계·안내로 나누되 과도한 범용 컴포넌트를 만들지 않는다. 데이터 조회·계산·쓰기를 View에 옮기지 않는다.

- `@StateObject` 모델을 하위 뷰 렌더링마다 다시 생성하지 않는다.
- `EditorTarget.newRecordID`를 폼 입력이나 테마 변경 때 다시 만들지 않는다. record ID는 같은 편집 세션에서 고정하지만 operation ID는 저장 시도마다 생성되는 기존 계약이다. 둘을 혼동해 operation ID까지 고정하지 않는다.
- 선택 날짜와 편집 대상 날짜를 분리한 현재 계약을 유지한다.
- 컴포넌트 분리로 `saveUnconfirmed`와 입력값이 초기화되지 않게 한다.
- 미확정 배너는 시트가 닫힌 뒤에도 같은 모델의 상태를 표시한다.

완료 조건: 추출 전후 저장·재확인 결과가 같고, 불필요한 저장 계층 변경이 없다.

### 4 기록 홈에 확정 디자인 적용

| 영역 | 구현 기준 |
| --- | --- |
| 날짜 줄 | 선택·오늘·기록 있음 표식을 구분. 현재 ±3일 탐색과 좌우 이동 규칙 유지 |
| 오늘/달력 | 이미 동작하는 진입점 유지. 지원하지 않는 히스토리 화면으로 바꾸지 않음 |
| 섭취 요약 | 기존 centigram 값을 포맷. 시각 표현을 위해 Double 합산하지 않음 |
| 목표 | `.goal`에만 진행률 표시. 범위는 0~100%로 제한하고 실제 합계는 그대로 표시 |
| 목표 초과 | 초과량과 달성 상태 표시. 매우 큰 값도 뺄셈 overflow 없이 처리 |
| 목표 없음 | 설명만 표시. 목표 화면 연결 전에는 가짜 링크/비활성 버튼을 넣지 않음 |
| 과거 목표 없음 | ‘목표 이력 없음’. 현재 목표로 달성 상태를 추정하지 않음 |
| 목표/합계 오류 | 오류 상태를 보여주며 0g·미설정으로 대체하지 않음 |
| 음식 행 | 긴 이름·소수량·출처를 표시. 말줄임 시 VoiceOver는 전체 이름을 읽음 |
| 이전 기록 | ‘원본 총량’과 ‘현재 합계에 반영되는 보정값’을 구분. 음수 부호 유지 |
| 추가 | 현재 가능한 직접 입력만 연결. 선택 날짜를 접근성 라벨에 포함 |

하단 내비게이션 A/B의 최종 연결은 후속 PR로 둔다. 이번에는 디자인을 맞춘 단일 추가 동작을 유지하며, 스크린샷 보고서에 최종 시안과 다른 이유를 기록한다.

접힌 레거시 요약에 보정값 10g을 ‘이전 하루 총량 10g’으로 표현하지 않는다. 원래 하루 총량 55g, 상세 45g, 보정 10g의 의미가 다른 만큼 명세의 문구도 필요한 범위에서 수정한다. 접힘에는 “이전 기록 보정 +10g”, 펼침에는 원본·음식 합계·보정·현재 총량을 구분한다. 합계만 있는 70g은 “이전 버전에서 가져온 하루 합계 70g”으로 표시한다. 음수 보정은 정상 데이터일 수 있으므로 음수만을 이유로 오류 색상을 강제하지 않는다.

완료 조건: 데이터 의미를 유지하면서 홈의 임시 스타일을 확정 스타일로 대체한다.

### 5 편집과 미확정 화면의 스타일 회귀 확인

기존 필드, 버튼, 오류 알림에 테마를 적용한다. 이 단계에서는 경고창을 인라인 검증으로 전환하지 않는다. 저장 동작과 오류 분기까지 동시에 바꾸지 않기 위해서다.

- 저장 중 취소·저장·삭제·필드가 기존 규칙대로 비활성이다.
- 미확정 중 필드는 잠기고 ‘저장 결과 확인’만 해당 작업을 확인한다.
- 재확인 실패 시 입력과 잠금이 남는다.
- 미반영이면 입력이 다시 활성화되고 같은 편집 세션 ID를 사용한다.
- 같은 프로세스에서 시트 닫기 후에는 홈 배너와 쓰기 차단 상태가 남는다. 초안은 보존되지 않는다.
- 홈 `.notApplied`에 현재 공통 문구인 “입력은 그대로 / Your input is kept; tap Save again”을 쓰지 않는다. 시트와 홈의 안내 컨텍스트를 분리하거나 양쪽에 사실인 중립 문구로 수정한다. 추가·수정·삭제·총량 변경에 모두 맞는 안내인지 확인한다.
- 미확정 시트의 상시 안내는 두 편집 시트 모두 적용한다. 홈 재확인은 초안 복구나 재저장이 아니라 저장 파일 읽기다.
- 키보드·큰 글자에서도 취소, 저장, 재확인에 접근할 수 있다.

완료 조건: 색상·레이아웃 변경으로 비활성 상태가 모호해지거나 버튼이 가려지지 않으며, 닫힌 시트의 초안이 남아 있다고 잘못 안내하지 않는다.

## 검증 데이터와 시나리오

아래는 합성 데이터다. 구체적인 날짜는 고정된 fixture 기준이며 실제 오늘과 혼동하지 않는다.

| 데이터 | 기대 결과 |
| --- | --- |
| 오늘 0g + 목표 120g | 빈 기록 안내와 0% 진행률 |
| 상세 31.5g + 8g + 12.2g | 합계 51.7g, 긴 영어 이름 표시 |
| 목표 120g + 총량 132g | 진행률 100%, 초과 12g |
| 과거 상세 10g + 35g + 보정 10g | 총량 55g, 원본·보정 구분 |
| 과거 합계만 70g | 빈 음식 상세와 레거시 안내, 목표 추정 없음 |
| 위 날짜에 18g 추가 후 총량을 75g으로 수정 | 상세 18g + 보정 57g = 75g, 가져온 원본 70g 유지 |
| 상세 20g + 보정 -5g | 총량 15g, 보정값 -5g 표시 |
| 목표 없음/잘못된 목표/합계 오류 | 각기 다른 설명, 임의 100g 목표 없음 |

검증 순서:

1. 기존 패키지와 앱 테스트를 변경 영향에 맞게 실행한다. 이전 기준은 코어 45개, 이관 64개, 앱 30개이나 단순 개수 유지보다 기존 계약 보존을 확인한다.
2. 새로운 표시 계산에 경계값 처리가 있으면 해당 계산만 단위 검증한다. 색상 상수나 뷰 계층을 그대로 복제하는 테스트는 만들지 않는다.
3. 시뮬레이터에서 날짜 이동 → 추가 → 수정 → 삭제 → 재실행을 확인한다.
4. 미확정의 반영/미반영/읽기 실패를 구분한다. 기존 DEBUG `-HelloProteinFailAfterReplaceOnce`는 교체 후 반영된 경로용이므로 이 한 번으로 모든 분기를 통과했다고 보고하지 않는다. 아래 재확인 매트릭스에 따라 테스트 대역과 앱 UI 증거를 나눠 남긴다. Release에 주입 코드가 활성화되지 않게 한다.
5. 영어/한국어, 기본 글자/접근성 큰 글자, 작은 화면/일반 화면을 확인한다. 다크는 지원하기로 결정했을 때 전체 상태를 검증한다.
6. VoiceOver의 날짜 전체 읽기, 선택 상태, 음식명·단백질량, 추가 대상 날짜, 진행률을 확인한다. 자동 접근성 트리 검사만 했다면 실제 VoiceOver 조작과 구분한다.
7. 날짜·이동·오늘·달력·추가·시트 버튼은 최소 44×44pt 터치 영역을 확보한다. 작은 화면에서 7일을 억지로 압축하지 않고, 큰 글자에서 행 높이 고정을 피하며 음식명/수치를 세로 배치할 수 있다. 선택·오늘·기록 있음은 색 외 표시도 사용한다. 키보드를 연 채 저장/재확인까지 도달하고, 애니메이션을 추가했다면 Reduce Motion을 확인한다.

### 저장 결과 재확인과 재실행 매트릭스

| 조건 | 기대 결과 | 증거 기준 |
| --- | --- | --- |
| 시트 유지 + 반영 | 재확인 후 닫힘, 정확히 한 번 반영 | 기존 DEBUG 교체 후 오류 경로 + UI |
| 시트 유지 + 미반영 | 입력 활성화, 초안/record ID 유지, 자동 재저장 없음 | 기존 VM 테스트 + 해당 상태를 재현한 UI |
| 재확인 읽기 실패 | 입력 잠금과 pending 유지, 재확인 가능 | 테스트 대역 + UI 상태 증거 |
| 시트 닫기 + 반영 | 홈 배너에서 읽기 확인, 결과 반영, 중복 없음 | 두 편집 시트에서 확인 |
| 시트 닫기 + 읽기 실패 | 홈 배너와 쓰기 차단 유지, 재확인 가능 | 대역 + 홈 UI |
| 시트 닫기 + 미반영 | 초안 보존/Save again을 약속하지 않는 홈 안내 | 재현용 대역 + 홈 문구 증거 |
| 앱 종료 후 재실행 | 검증된 디스크 상태를 읽거나 해당 복구 경로 진입, 원본 손상·중복 없음 | 실제 종료/재실행과 파일 검증 |

`pendingSave`, 경로별 쓰기 차단 및 미확정 operation ID는 프로세스 메모리 상태다. 재실행 후 배너·초안·미확정 ID의 영속 복원을 기대하지 않는다. “데이터 보존”은 저장된 기록과 이관 원본을 뜻하며 저장되지 않은 시트 초안까지 보장하지 않는다.

실제 fixture 준비 절차·기준 날짜·실행 날짜·시간대·선택 날짜·입력 순서·주입 방법을 증거에 적는다. `LegacyFixtureSeeder`는 기존 저장 증거/UserDefaults 목표/Realm 행이 있으면 실행하지 않으므로 별도의 빈 검증 환경에서 시드 성공을 확인한다. 시드 인자를 다시 켰다고 초기화됐다고 가정하지 않는다. 51.7g·132g·음수 보정·오류 상태는 기본 시더가 모두 제공하지 않으므로 추가 준비 절차를 기록한다. 현재 도구로 특정 UI 분기를 재현할 수 없다면 테스트 전용 대역/하네스의 최소 추가 범위를 먼저 산정한다. 제품 저장 계약을 고쳐 상태를 억지로 만들지 않는다. 재현하지 못한 셀은 미검증으로 남기고 해당 완료 조건을 체크하지 않는다.

### 문구 검토 기준

원본은 `Original imported total`, 보정은 `Adjustment`, 음식 합은 `Food entries`, 현재 합계는 `Daily total`처럼 의미를 분리한다(영어 카피 제안, 원어민 검증 완료 아님). 총량 수정 후에는 보정을 항상 “원본과 음식의 차이”라고 설명하지 않는다. 원본 70g·상세 18g·현재 합계 75g·보정 57g을 넣어 문구가 여전히 참인지 확인한다.

미확정은 실패로 단정하지 않고 결과 확인 동작을 안내한다. 홈/시트에 공통 안내를 쓴다면 `This change wasn’t saved. Please make the change again.`처럼 초안 보존을 약속하지 않는 내용을 검토한다. 추가·수정·삭제·총량 변경 모두에 맞아야 하며 파일 교체 같은 구현 용어는 사용자 안내에서 덜어낸다.

### 과업 점검

각 과업별 성공/실패/미실행, 언어, 시작 상태, 막힌 지점과 수정 후 재확인 결과를 기록한다. 선택한 과거 날짜에만 추가·수정이 반영되고, 재확인은 새 저장을 유발하지 않아야 한다.

기획·디자인·QA가 한국어와 영어에서 과거 날짜 선택→수정→합계 확인, 합계만 있는 날짜 이해, 저장 실패와 결과 재확인 구분을 점검한다. 경로·막힌 지점·문구 오해를 기록한다. 담당자 점검과 실제 사용자 테스트를 구분하며, 사용자 반응 데이터 없이 리텐션이 개선됐다고 결론 내리지 않는다.

캡처는 `docs/evidence/<실행일>-ui-phase1/`에 보관한다. 동일 기기·언어·글자 크기·fixture의 전후 화면을 비교하고, 시안과 달라진 부분은 사유를 적는다. 시각 회귀를 무조건 픽셀 완전 일치로 판정하지 않는다.

기존 검증 명령 참고:

```sh
swift test --package-path HelloProteinCore --scratch-path /private/tmp/helloprotein-ui-phase1-core
swift test --package-path MigrationCore --scratch-path /private/tmp/helloprotein-ui-phase1-migration
xcodebuild -project ProteinTracker/ProteinTracker.xcodeproj \
  -scheme ProteinTracker -configuration Debug \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /private/tmp/helloprotein-ui-phase1-build \
  -onlyUsePackageVersionsFromResolvedFile -disableAutomaticPackageResolution \
  build CODE_SIGNING_ALLOWED=NO IPHONEOS_DEPLOYMENT_TARGET=15.0
```

앱 통합 테스트는 설치된 simulator ID와 실제 테스트 scheme을 확인한 후 `xcodebuild test`로 실행한다. 명령행의 iOS 15 지정은 현재 빌드 환경용이며 프로젝트 지원 OS 변경이 아니다. 시뮬레이터 조작은 해당 환경의 `orca-emulator` 스킬을 확인한 뒤 수행한다.

자정·주 시작·스와이프 날짜 탐색은 Phase 1B의 안전 UX와 구분해 우선순위를 정한다. Phase 1 완료는 출시 준비 완료가 아니다.

목표 설정을 계획할 때 신규 설치 구분은 `migration.origin` 등 실제 저장 계약을 기준으로 설계한다. 신규 설치도 완료 메타데이터를 생성하므로 ‘이관 증거 파일 없음’만으로 온보딩을 판단하지 않는다.

## 인계할 지시

> 이 문서와 공동 검토 기록을 읽고 Phase 1을 진행해줘. 시작 시 최신 main/작업 상태를 확인하고 기존 변경을 보존해줘. 이번 홈·추가 배치, 브랜드, 테마의 미확정 항목만 실제 적용 영역이 보이는 비교 화면으로 확인받고, 이미 받은 답은 다시 묻지 마. 최종 A/B 내비게이션은 후속이다. 확정 후 Renewal 테마·홈·기존 편집 시트 표현만 바꾸고 미확정 초안 미보존 안내와 홈/시트 미반영 문구를 수정해줘. 저장·이관 계약, record ID와 operation ID 각각의 수명은 보존해줘. 미구현 메뉴·AI·과금·출시로 넓히지 마. fixture별 준비 절차와 전후 캡처, 재확인 매트릭스, 실제 명령/종료 코드/미검증을 보고해줘. 미확정 닫기 확인창은 Phase 1B로 남기되 완료했다고 쓰지 마. 문서/소스 충돌은 실제 코드 근거로 보고하고 저장 계약이나 사용자 미결정 디자인을 임의로 확정하지 마. 이 계획만으로 커밋·푸시·병합·기본 활성화까지 요청받은 것으로 해석하지 마.
