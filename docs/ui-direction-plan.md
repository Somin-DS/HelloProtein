## 1. 이번 작업의 목적

기존 앱, 사용자가 제공한 두 Figma 문서, 현재 SwiftUI 프로토타입을 비교하여 **최종 UI의 기준과 화면별 동작을 정한다.** 기능 검증을 위해 임시로 정한 색상·레이아웃·기본 컴포넌트가 최종 디자인으로 굳어지는 것을 방지한다.

현재 사용자는 UI가 어떤 근거로 크게 변경됐는지 확인을 요청했다. 따라서 다음 작업은 목표 설정이나 즐겨찾기를 바로 구현하는 단계보다 먼저 수행한다.

이 문서는 다른 AI 에이전트에게 전달할 실행 계획이다. 문서 작성 시 제품 코드, Figma, 저장 데이터는 변경하지 않았다. 아래 화면 구조는 검토 출발점이며 사용자에게 이미 승인받은 최종안이 아니다.

## 5. 실행 순서

### A. 기존 사용 경험과 현재 변경을 조사

검토할 구현 위치:

- 기존 홈: `ProteinTracker/ProteinTracker/StoryBoard/Base.lproj/Show.storyboard`, `ViewController/ShowViewController.swift`.
- 기존 추가·검색: `StoryBoard/Add.storyboard`, `ViewController/AddViewController.swift`, `ViewController/SearchViewController.swift`.
- 기존 통계·설정: `StoryBoard/Stats.storyboard`, `StoryBoard/Setting.storyboard`, 대응 ViewController.
- 기존 온보딩: `StoryBoard/Init.storyboard`, `ViewController/InitViewController.swift`.
- 새 화면: `Renewal/RecordHomePrototypeView.swift`, `RecordHomeViewModel.swift`.
- 시작/복구: `Migration/RenewalLaunchPolicy.swift`, `RecoveryViewController.swift`.

위 경로는 앱 디렉터리 `ProteinTracker/ProteinTracker/` 기준이다. 기존 화면의 폰트·색상·아이콘·앱 자산도 함께 확인한다.

비교 항목은 홈 요약, 날짜 탐색, 기록 추가, 과거 편집, 목표, 즐겨찾기, 히스토리, 설정, 오류/복구다. 각 항목에 다음을 기록한다.

```text
기존 앱의 행동 → Figma의 의도 → 현재 구현 → 유지/변경/미결정 → 변경 이유
```

화면을 실행한다면 합성 fixture를 사용한 별도 시뮬레이터/데이터 영역을 쓴다. 이관된 설치를 강제로 구 흐름에 넣지 않는다. 환경의 시뮬레이터 스킬을 먼저 읽고 원본/현재 화면의 기기 크기와 데이터 조건을 맞춘다.

완료 기준: 무엇이 Figma에서 왔는지, 사용자 요구에서 왔는지, 구현자가 임시로 정했는지 추적 가능하다.

### B. 핵심 사용자 흐름을 먼저 정리

최소 다음 흐름을 시안에서 따라갈 수 있게 한다.

1. 기존 사용자: 앱 열기 → 오늘 합계 확인 → 음식 추가 → 합계 갱신.
2. 과거 누락 보완: 날짜 선택 → 기록 추가 → 같은 날짜의 목록/합계 확인.
3. 과거 수정: 음식 선택 → 양 수정 또는 삭제 → 합계 갱신.
4. 합계 전용 기록: 과거 날짜 열기 → 상세가 없는 이유 확인 → 합계 수정 또는 새 음식 추가.
5. 신규 사용자: 목표 직접 입력 → 홈 진입. 계산기는 선택적 보조 흐름으로 표시한다.
6. 목표 변경: 목표 편집 → 적용일과 의미 확인 → 해당 날짜부터 반영.
7. 저장 실패: 입력 유지 → 오류 해결 → 재시도.
8. 결과 미확정: 입력 잠금 → 읽기 재확인 → 확정 후 화면 갱신.

목표 설정·즐겨찾기·검색은 설계하되 실제 서비스 연결은 후속 구현으로 표시한다. 아직 없는 기능이 작동하는 것처럼 제품 화면에 넣지 않는다.

### C. 화면 트리 권장안 작성

디자이너 와이어프레임을 출발점으로 아래 구조를 검토한다.

```text
시작 판정
├─ 이관/복구 상태
├─ 신규 사용자 목표 설정
└─ 홈: 선택 날짜의 기록
   ├─ 날짜 탐색 / 오늘 복귀
   ├─ 섭취 요약 / 목표
   ├─ 음식 기록 → 편집 시트
   ├─ 이전 버전 합계 → 합계 편집 시트
   ├─ 추가 → 직접 입력 / 검색 / 즐겨찾기
   ├─ 히스토리 → 캘린더 / 그래프 → 날짜 기록
   └─ 설정 → 목표 / 검색 언어 / 앱 정보
```

이 트리는 진입 관계 초안이지 최종 탭 선언이 아니다. 다음을 구체적으로 결정한다.

- Figma의 ‘히스토리 / 중앙 추가 / 설정’을 홈의 하단 액션으로 둘지, 독립 내비게이션으로 둘지.
- 추가 버튼은 이동 탭이 아니라 입력 시작 동작임을 시각·접근성에서 명확히 할 방법.
- 히스토리에서 날짜를 선택하면 홈으로 이동할지, 동일한 기록 컴포넌트를 상세 화면으로 보여줄지.
- 홈 날짜 선택과 히스토리 선택을 어떻게 유지하고, 뒤로 가기에서 어디로 돌아올지.
- 목표 편집의 주 진입점과 홈의 보조 진입점.
- 저장하지 않은 입력이 있는 상태에서 닫기·날짜 변경·뒤로 가기의 동작.

권장안 하나를 중심으로 제시한다. 큰 구조적 대안이 필요한 경우에만 대안 하나를 같은 조건으로 비교한다. 사소한 간격·색상 선택까지 사용자 질문으로 넘기지 않는다.

### D. 시각 기준과 화면 상태 설계

기존 자산에서 유지할 브랜드 요소를 먼저 찾는다. 근거 없이 전체 브랜드를 교체하거나 현 프로토타입의 초록색을 브랜드 색으로 확정하지 않는다.

토큰 초안은 의미·값·출처를 함께 기록한다.

- 배경/표면/주요 동작/텍스트/선택/오류 색상.
- 섭취량 숫자, 화면 제목, 본문, 보조 설명의 글자 크기·굵기.
- 화면 여백, 목록 간격, 버튼 크기, 모서리, 구분선.
- 날짜 선택, 음식 행, 섭취 요약, 추가 버튼, 편집 폼의 공통 형태.

날짜 선택과 목표 달성을 색상 하나로 혼합하지 않는다. 진행률은 조작 가능한 슬라이더처럼 보이지 않게 한다. 과거 목표를 모르면 달성/미달을 추정하지 않는다.

다음 상태를 시안에 포함한다.

| 화면 | 필수 상태 |
| --- | --- |
| 홈 | 오늘 빈 상태, 기록 있음, 목표 없음, 목표 초과 |
| 날짜 기록 | 과거 상세 있음, 합계만 있음, 합계+추가 상세, 음수 보정값 |
| 추가/편집 | 직접 입력, 검증 오류, 키보드 표시, 저장 중, 저장 실패 |
| 미확정 저장 | 필드 잠금, 재확인 가능, 재확인 실패, 미반영 후 입력 재개 |
| 목표 | 기존 목표, 신규 입력, 잘못된 기존 값 확인, 과거 이력 없음 |
| 검색/즐겨찾기 | 비어 있음, 긴 이름, 여러 항목 선택, 선택 날짜·합계 확인 |
| 히스토리 | 캘린더/그래프 전환안, 선택 날짜 상세 진입 |
| 복구 | 원본 보존 설명, 재시도 가능한 상태, 재시도로 해결되지 않는 상태 |

모든 내부 값을 홈에 펼쳐놓을 필요는 없다. 이관 원본 총량·보정값·사용자 수정값은 보존하되, 일반 사용자가 이해할 수 있는 요약과 필요 시 상세 설명으로 표현한다. ‘이전 기록 없음’과 ‘합계만 있음’을 혼동시키지 않는다.

### E. 검토 가능한 시안 제작

긴 설명 문서만 내지 말고 최소 홈·과거 기록·추가/편집·목표·내비게이션을 한 흐름으로 확인할 수 있는 시안을 제공한다.

권장 형태는 로컬 HTML/CSS 기반 클릭 가능한 시안 또는 환경에서 제공 가능한 UI 프리뷰다. 이는 제품 구현과 분리하며 실제 저장소에 연결하지 않는다. 검토에 필요한 이동·시트 동작만 구현하고, 검색 서버나 결제 등 범위 밖 기능을 만들지 않는다.

- 기존 앱 캡처, Figma 참고, 권장안을 같은 크기로 비교한다.
- 데이터는 영어의 긴 음식 이름, 소수량, 빈 날짜, 레거시 합계 날짜를 포함한 공통 fixture를 쓴다.
- 영어와 한국어, 작은 화면과 큰 글자에서 주요 흐름을 확인한다.
- 아직 구현하지 않은 기능은 프리뷰 안내에서 명확히 표시한다.
- 기존 자료에 없는 시각 결정을 ‘새 제안’으로 표시한다.
- 사용자 Figma 원본에는 쓰지 않고 로컬 산출물로 검토 가능하게 한다.

앱 화면처럼 정확한 텍스트와 인터랙션이 필요한 시안은 코드 기반 도구를 우선한다. 전체 화면을 이미지 생성으로 대체하지 않는다.

### F. 결정과 후속 구현 backlog 정리

시안을 완성한 뒤 핵심 결정만 사용자에게 제시한다. 주요 질문은 ‘화면 구조’와 ‘기존 브랜드 유지 범위’다. 설명만으로 승인을 요청하지 말고 비교 시안을 함께 제공한다.

이 검토 지점은 이번 계획의 작업 범위가 UI 기준 합의까지이기 때문에 둔다. 이전에 기능 구현이나 병합을 승인받았다는 사실을 새 디자인 승인으로 해석하지 않는다. 사용자 답변 전에는 `권장안 / 미확정`으로 남기며 제품 화면 교체를 시작하지 않는다.

후속 구현 backlog는 다음 순서로 작성한다.

1. 확정된 토큰·공통 컴포넌트와 기록 홈의 시각 정리.
2. 날짜 탐색·과거 기록·편집 시트·복구 상태의 UX 정리.
3. 목표 설정/수정과 목표 이력 연결.
4. 즐겨찾기·검색·다중 추가 연결.
5. 히스토리·설정 완성 및 출시 전 검증.

각 항목에는 현재/목표 동작, 변경 파일, 데이터 의존성, 시각 확인 항목, 기능 회귀 검사를 적는다. UI 구조가 바뀌어도 이미 검증된 저장 로직을 함께 재작성하지 않는다.

## 6. 절대 유지할 동작 계약

- 편집 대상 날짜는 시트를 연 시점에 고정한다.
- 저장 성공을 확인한 뒤 목록과 합계를 반영한다.
- 실패 시 입력을 유지하고, 미확정 저장을 일반 재저장으로 처리하지 않는다.
- 저장 중·미확정 중에는 이름·단백질·총량 입력을 잠근다.
- 같은 추가 작업 재시도로 음식이 중복되지 않는다.
- 이관된 합계만 있는 날짜에 가짜 음식 상세를 생성하지 않는다.
- 상세+signed 보정값으로 합계를 계산하고, 음수 보정값을 임의로 0으로 바꾸지 않는다.
- 기존 목표의 과거 적용 시점을 추정하지 않는다.
- 기존 사용자에게 초기 온보딩을 다시 강제하거나 즐겨찾기 제한을 새로 부과하지 않는다.
- 검토 편의를 위해 구 저장소로 돌아가 쓰거나 원본 데이터를 지우지 않는다.

## 7. 완료 기준과 검증 범위

- [ ] 기존 앱/Figma/현재 화면의 차이와 출처를 비교했다.
- [ ] 큰 UI 변경의 이유를 설명할 수 있고, 임시 구현을 최종안으로 둔갑시키지 않았다.
- [ ] 화면 트리와 뒤로 가기·날짜 유지·추가 진입 동작이 정의됐다.
- [ ] 비교 가능한 시안과 주요 상태가 제공됐다.
- [ ] 영어·한국어, 긴 이름, 큰 글자, 키보드 상태를 확인했다.
- [ ] 데이터/저장 계약이 UI 설계에서 유지된다.
- [ ] 사용자 확정 사항과 에이전트 권장안을 구분했다.
- [ ] 후속 구현 작업이 파일·의존성·검증 기준까지 나뉘어 있다.
- [ ] 제품 코드·저장 데이터·Figma 원본·출시 설정은 변경하지 않았다.

이번 단계는 디자인 조사와 시안 작업이므로 제품 단위 테스트를 반복 실행하는 것이 핵심 완료 조건은 아니다. 프리뷰의 이동·상태·레이아웃을 직접 확인하고, 기능 구현이나 앱 실행을 하지 않았다면 미실행으로 보고한다. 확인하지 않은 접근성·색상 대비·실기기 동작을 통과했다고 쓰지 않는다.

자료 접근 제한이 있으면 어디까지 확인했는지 적는다. 필요한 자료를 보지 못한 상태에서 ‘Figma와 일치’ 또는 ‘사용자 승인 완료’로 결론 내리지 않는다.

## 8. 다른 에이전트에게 전달할 지시

> `docs/ui-direction-plan.md`에 따라 UI 기준 정리 작업을 진행해줘. 기존 앱·두 Figma·현재 SwiftUI 프로토타입을 비교하고, 권장 화면 구조와 디자인 기준을 검토 가능한 시안으로 만들어줘. 현재 초록색/기본 SwiftUI 화면을 확정 디자인으로 가정하지 말고, 관찰한 자료와 새 제안을 구분해줘. 제품 코드·저장소·Figma 원본은 수정하지 말고, 비교 문서·UI 명세·시안·후속 구현 backlog를 작성해줘. 시안이 준비되면 사용자가 결정해야 할 큰 항목만 정리해서 보여줘. 이미 구현된 이관·저장 안전성은 유지하고 Android·AI·결제로 범위를 넓히지 마.
