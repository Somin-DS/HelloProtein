# Phase 1B 편집 확인과 저장 결과 안내 구현 계획

작성일: 2026-10-06. 대상: 다음 구현 에이전트와 리뷰 담당자.

> 2026-10-06 구현 상태: 이 계획의 Phase 1B를 `feat/renewal-phase1b-editing` 브랜치에 구현했다. 실행 결과·캡처·미검증은 [실행 증거](evidence/2026-10-06-phase1b/README.md)에 기록한다. iOS 15 런타임·실기기·VoiceOver는 미검증이며 새 흐름 기본 활성화·출시는 하지 않았다.

다음 작업은 **기록 입력 중 닫기와 삭제를 확인하고, 저장 결과를 알 수 없는 상태에서 안전하게 다음 행동을 안내하는 것**이다. 목표 설정이나 새 기능 연결에 앞서 기존 편집 흐름을 마무리한다. 본사 7개 직무가 검토했으며 역할별 근거와 범위 조정은 [공동 검토 기록](reviews/2026-10-06-phase1b-team-review.md)에 남긴다. 이 문서는 구현 계획이며 이번 작성에서 제품 코드를 변경하거나 새 테스트를 실행하지 않았다.

## 현재 기준

- [PR #5](https://github.com/Somin-DS/HelloProtein/pull/5)는 2026-10-05 main에 병합됐다. 머지 커밋은 `64b9688ee674a8bdb831ea4298f1cfeb847f05ab`, 마지막 구현 커밋은 `3735913acd1c692ba9926c69f64c0235cdafe9e5`다.
- 현재 로컬은 `feat/renewal-home-phase1`의 `3735913`에 있다. 구현 착수 시 최신 main과 비교하고 병합된 내용을 기준으로 작업한다. `.DS_Store`와 `agents/` 등 무관한 사용자 파일은 삭제하거나 일괄 stage하지 않는다.
- 직전 실행 결과는 Core 45개, MigrationCore 64개, 앱 33개와 별도 SE·17 UI 6개 통과다. 이는 이번 구현의 통과 결과가 아니다. [실행 증거](evidence/2026-10-05-iphone-ui/README.md)를 참고한다.
- 일반 iPhone 세로 화면을 기준으로 한다. Duo 동시 대응은 사용자 결정에 따라 연기한다. 현재 테마·날짜 탐색·단일 추가 버튼을 유지한다.
- 새 흐름은 여전히 플래그 뒤에 있고, 새 저장소 증거가 있으면 플래그와 관계없이 새 흐름을 쓰는 시작 정책도 유지한다.

## 다음 작업으로 선택한 이유

`RecordHomePrototypeView.swift`의 두 편집 시트는 취소 버튼이 곧바로 `dismiss()`를 호출한다. 스와이프는 `model.isBusy`일 때만 막는다. 기록 삭제도 버튼을 누르면 바로 실행된다. 이미 입력한 내용을 잃거나 기록을 실수로 지울 수 있는 빈틈이 남아 있다.

목표 설정과 즐겨찾기는 반복 사용에 중요하지만, 기존 계획에서도 이 편집·복구 UX 다음 순서다. 이번에는 입력과 저장 상태의 의미를 먼저 명확히 한다. 사용자 제공 누적 다운로드 수를 현재 활성 사용자나 구독 의향의 증거로 취급하지 않는다.

## 변경 감지 기준

각 편집 시트가 열릴 때 최초 표시 문자열을 스냅샷으로 보관한다.

- 신규 기록은 초기 음식명과 단백질량이 모두 빈 문자열이다.
- 기존 기록은 실제 표시된 음식명과 지역화된 단백질량 문자열이 초기값이다.
- 하루 합계 편집은 실제 표시된 합계 문자열이 초기값이다.
- 현재 문자열이 초기 문자열과 하나라도 다르면 변경 있음이다. 공백 추가나 `10`을 `10.0`으로 바꾸는 것도 변경으로 본다. 원래 표시 문자열로 되돌리면 변경 없음이다.
- 이 비교를 위해 저장 파서를 수정하거나 입력을 강제로 정규화하지 않는다. 잘못된 숫자를 입력한 경우에도 초안을 버리는 확인이 필요하다.
- 확인창에서 계속 입력을 선택해도 값, 선택 날짜, 편집 세션의 record ID가 유지돼야 한다. SwiftUI 재렌더링마다 초기 스냅샷을 새로 만들지 않는다.

## 닫기 정책

취소 버튼과 스와이프 시도는 하나의 정책을 사용한다. 우선순위는 **처리 중 → 미확정 → 변경 있음 → 변경 없음**이다.

| 현재 상태 | 취소 버튼 또는 스와이프 시도 | 결과 |
| --- | --- | --- |
| 변경 없음, 처리 중 아님 | 즉시 닫기 | 쓰기 없음 |
| 변경 있음, 처리 중 아님 | 버리기 확인 | 계속 입력은 유지, 버리고 닫기는 초안만 폐기 |
| 저장 또는 재확인 중 | 닫기 차단 | 새 확인창이나 새 쓰기 없음 |
| 저장 결과 미확정 | 변경 여부와 관계없이 미확정 닫기 확인 | 머무르기는 유지, 닫기는 시트만 닫고 홈 pending과 쓰기 차단 유지 |
| 입력 오류 또는 저장 전 실패 | 오류 안내 종료 후 변경 감지 정책 적용 | 입력 유지, 저장이 일어나지 않은 확인창 취소는 무변경 |

정상 저장 또는 재확인 성공으로 프로그램이 시트를 닫을 때는 사용자 닫기 확인을 다시 띄우지 않는다.

미확정 시트 닫기는 이미 시도한 저장이나 삭제를 취소하는 동작이 아니다. 닫은 뒤 홈에서 저장 결과 확인을 누를 수 있다. 초안은 영속 저장되지 않는다. 확인창의 ‘화면에 머무르기’도 재확인을 자동 실행하지 않는다.

확인창을 표시한 뒤 사용자가 결정을 내리기 전 상태가 바뀔 수 있다. 실제 확인 버튼 handler에서도 최신 busy/pending 상태를 다시 검사한다. 오류 alert와 버리기·삭제·미확정 닫기 확인이 겹치지 않도록 표시 상태를 하나의 enum 등으로 직렬화한다. 이미 alert가 떠 있으면 뒤에 숨은 다른 확인창을 예약해 중복 실행하지 않는다.

## 삭제 정책

삭제 확인에는 **저장된 기존 기록**의 이름(없으면 직접 입력), 날짜, 단백질량을 표시한다. 아직 저장하지 않은 입력란의 값으로 삭제 대상을 설명하지 않는다.

취소는 아무 것도 쓰지 않는다. 확인 시에만 기존 `deleteRecord`를 한 번 호출한다. 빠른 연속 탭도 한 번만 실행하며 busy/pending 상태에서는 새 삭제가 실행되지 않는다. 삭제 성공이면 닫고, 저장 전 실패면 편집 화면과 입력을 유지한다. 삭제 결과 미확정이면 일반 미확정 정책으로 들어가고 ‘삭제 완료’라고 표시하지 않는다. 삭제 후 재확인에서 미반영으로 판정되면 기존 기록이 남아 있으며 다시 삭제할 수 있어야 한다.

## 저장 결과별 동작

| 결과 | 시트에서 확인했을 때 | 홈에서 확인했을 때 |
| --- | --- | --- |
| 정상 저장 또는 재확인 결과 반영됨 | 확인된 최신 상태 적용 후 닫기 | 배너·쓰기 잠금 해제, 확인된 상태 표시 |
| 입력 오류 | 기존 오류 분류 안내, 입력 유지 | 해당 없음 |
| 교체 전 저장 실패 | 입력 유지, 재시도 가능 | 해당 없음 |
| 재확인 결과 미반영 | 잠금 해제, 입력 유지, 작업 다시 수행 가능 | 잠금 해제, 중립 문구 안내; 닫은 초안이 복원됐다고 말하지 않음 |
| 재확인 읽기 실패 | 입력·미확정 상태·쓰기 차단 유지 | 배너·쓰기 차단 유지 |

`reconfirm()`은 저장소를 읽는 동작이다. 재저장, 자동 재시도, rollback으로 바꾸지 않는다. 같은 편집 세션의 record ID는 유지하고, operation ID는 기존처럼 저장 시도마다 생성한다. 시트의 고정 대상 날짜와 현재 홈 선택 날짜도 혼동하지 않는다.

동일 프로세스에서 시트를 닫은 경우와 프로세스를 종료했다가 실행한 경우를 구분한다. pending과 초안은 메모리 상태다. 재실행은 시작 경로에서 디스크를 읽어 판단하며 이전 pending 배너나 초안의 복원을 약속하지 않는다. 파일이 정상이라면 실제 저장된 행을 한 번만 보여주고, 파일에 문제가 있으면 기존 복구 판정으로 진입한다.

## 복구 화면

현재 UIKit `RecoveryViewController`를 유지한다. SwiftUI로 전면 이식하거나 새 복구 로직을 만들지 않는다.

- 제목은 이관 실패뿐 아니라 저장 파일 문제도 포함하는 ‘기록을 열 수 없어요 / Unable to open your entries’를 기준으로 정리한다. unsupportedOS에는 기존 지원 OS 안내를 유지한다.
- `RecoveryState.kind`, `canRetry`, `originalPreserved`, `backupAvailable`이 안내의 근거다. `ui-spec`의 원본 보존 문장을 ‘항상 표시’한다는 오래된 지침보다 실제 조건을 우선한다.
- 원본 보존 문장은 `originalPreserved`일 때만, 백업 안내는 `backupAvailable`일 때만 표시한다. 백업 존재를 복원 성공 보장으로 바꾸지 않는다.
- 재시도 버튼과 ‘다시 시도’ 안내는 `canRetry && retry callback 존재`일 때 함께 표시한다. 동작이 없는 버튼·재시도 안내를 만들지 않는다.
- 재시도 가능 안내: ‘다시 시도해 기록을 열 수 있는지 확인해 주세요. / Try again to check whether your entries can be opened.’ 불가 상태에는 현재 상태 설명을 유지하며 복구 불가능이라고 단정하지 않는다.
- 재시도는 기존 시작 판정을 다시 실행한다. 재시도 중 연속 탭을 막고, 결과에 따라 로딩·홈·복구 화면으로 기존 흐름대로 이동한다.
- 삭제·초기화·덮어쓰기·강제 구버전 복귀 동작을 추가하지 않는다. Release 화면에 원시 데이터나 민감한 오류 상세를 노출하지 않는다.
- 기존 문의 수신처가 소스에 있다는 것만으로 운영 중인 지원 채널이라고 확정하지 않는다. 문의 연결은 채널·사용자 직접 전송·메일 미설정 fallback을 검증하는 별도 후속 작업으로 둔다.

| `docs/evidence/<실행일>-phase1b/` | 실제 시나리오, fixture, 캡처, 로그와 미검증 |

SwiftUI의 `.interactiveDismissDisabled`만 추가하면 스와이프가 조용히 막혀 확인창을 볼 수 없다. iOS 15에서 실제 presented hosting controller의 `UIAdaptivePresentationControllerDelegate` 등 화면 범위의 어댑터를 검토한다. `shouldDismiss`와 `didAttemptToDismiss`가 동일 정책을 사용하고 SwiftUI의 내부 delegate와 충돌하지 않는지 확인한다. 참조는 적절히 약하게 보관하며 시트 교체·해제 시 정리한다. 시스템 전역 swizzling이나 전역 appearance는 사용하지 않는다. iOS 16 이상 전용 API로 최소 OS를 올리지 않는다.

## 작업 순서

1. main과 작업 상태 확인, 기존 동작과 상태 표를 테스트 fixture로 고정한다. 미확정 주입 방식과 Release 분리를 먼저 설계한다.
2. 초기 스냅샷과 닫기 정책을 만들고 일반 취소 확인을 두 시트에 적용한다. 삭제 확인을 추가한다.
3. 스와이프 시도를 동일 정책에 연결한다. 확인창 유지/폐기/처리 중 차단과 presentation 경합을 검증한다.
4. 미확정 닫기와 재확인 결과별 안내를 검증한다. 기존 store·VM의 저장 계약을 유지한다.
5. UIKit 복구 화면의 조건부 설명과 재시도 접근성을 정리한다.
6. 일반 iPhone에서 실제 조작·캡처, 회귀 검사, Release 테스트 코드 분리 확인 후 PR로 정리한다. 출시 활성화는 별도다.

## 테스트 설계

기존 `HelloProteinFailAfterReplaceOnce`는 실제 파일 교체 이후 실패와 이후 읽기로 확인하는 경로만 재현한다. 이것 하나로 미반영·읽기 실패까지 검증했다고 보고하지 않는다. 기존 VM 테스트의 `IndeterminateOnceStore` 등 대역을 참고해 테스트 타깃 또는 DEBUG 조립 접점에서 반영/미반영/읽기 실패를 결정적으로 만든다. 기존 파일 rollback이나 실제 사용자 파일 권한 변경으로 상태를 흉내 내지 않는다. 대역은 UI 상태 계약 검증이며 실제 디스크 내구성 검증과 구분한다. Release에는 새 주입 인자·경로가 포함되지 않아야 한다.

| 검증 축 | 필수 사례와 기대값 |
| --- | --- |
| 변경 감지 | 신규 빈 입력, 기존 기록, 총량, 공백·형식 변경, 잘못된 숫자, 원래 문자열로 복귀 |
| 닫기 경로 | 세 편집 유형 × 취소/스와이프 × 계속 입력/버리기. 유지 시 입력·날짜·record ID 동일, 버리기는 store write 0 |
| 삭제 | 저장된 대상 식별, 취소 write 0, 확인 delete 1회, 빠른 연속 탭, 저장 전 실패·미확정 |
| busy | 저장과 재확인 지연 중 취소·스와이프·삭제·새 저장 불가. 완료 후 정상 전이 |
| 미확정 시트 | dirty보다 우선, 머무르기 유지, 닫기 후 홈 배너·쓰기 차단 유지. 음식/총량 시트 모두 |
| 재확인 | 반영/미반영/읽기 실패 × 시트/홈. 읽기만 호출, 중복 추가 없음, 삭제 미반영은 행 유지 |
| presentation 경합 | 오류 alert 종료 전 새 확인창 중첩 없음. 확인 버튼 동작 시 최신 busy/pending 검사 |
| 재실행 | 프로세스 종료 전후 실제 파일·행 수·ID 확인. 초안/메모리 pending 복원으로 오인하지 않음 |
| 복구 | 원본/백업 플래그 true/false, retry 가능/불가/callback 없음, unsupportedOS, 큰 글씨·재시도 연속 탭 |
| 보존 | 원본 Realm/UserDefaults·이관 증거 불필요한 변경 없음. 날짜·원본 총량·signed 보정 계약 유지 |

SE 3세대와 iPhone 17(iOS 26.5, `/Applications/Xcode.app`, 명령별 `DEVELOPER_DIR`)을 기존 검증 환경으로 사용할 수 있다. 설치 상태는 재확인한다. 기존 합성 fixture가 누적돼 있으므로 실행일과 날짜·초기값·작업 순서·기대 합계를 명시한다. 과거 하네스를 그대로 반복 실행해 132g 같은 고정 합계를 가정하지 않는다.

한영·키보드 표시·AX3에서 확인 문구와 선택 버튼을 실제로 조작한다. 접근성 트리 존재만으로 보인다고 판단하지 말고 탭 후 결과를 확인한다. 확인 선택의 터치 영역은 최소 44pt를 확보한다. 확인창에서 계속 입력을 선택하면 편집 필드로, 시트를 닫으면 홈의 해당 진입 버튼으로 VoiceOver 초점이 적절히 돌아오는지 확인한다. VoiceOver 초점·발화는 별도로 실제 확인하고, 못 하면 미검증으로 남긴다. 320pt 호스팅 검사는 좁은 폭 회귀에 사용하되 iOS 15 실기기 검증으로 표현하지 않는다.

앱 빌드·관련 단위/통합 테스트·Core/MigrationCore 회귀를 실행한다. 테스트 개수를 고정 완료 목표로 삼지 말고 실패/스킵과 범위를 기록한다. `git diff --check`, 프로젝트·한영 strings 구문 검사, Debug/Release 분리 확인을 포함한다.

## 완료 기준과 증거

- [ ] 취소와 스와이프가 상태 표대로 동작하며 스와이프를 무반응으로 막는 것으로 끝내지 않음.
- [ ] 일반 확인·삭제 확인·미확정 닫기 확인이 겹치지 않고 각 취소는 데이터 무변경.
- [ ] 저장/재확인 중 경합 차단, 같은 세션 record ID와 대상 날짜 유지.
- [ ] 미반영·읽기 실패를 포함한 상태별 UI 검증과 실제 afterReplace 재확인 검증을 구분해 기록.
- [ ] 복구 안내가 실제 플래그와 CTA 조건에 맞고 원본·백업·복원에 거짓 보장을 하지 않음.
- [ ] 일반 iPhone 두 크기의 한영·키보드·AX3 주요 경로 캡처와 실행 결과 확보.
- [ ] 저장·이관·스키마·기본 활성화 정책 회귀 없음, Release에 테스트 주입 없음.
- [ ] iOS 15 런타임·실기기·VoiceOver 등 미검증을 숨기지 않고 PR에서 명시.

캡처 예: `discard-entry.png`, `discard-total.png`, `delete-confirm.png`, `pending-close.png`, `pending-home.png`, `not-applied-sheet.png`, `not-applied-home.png`, `reconfirm-read-failed.png`, `recovery-retry.png`, `recovery-no-retry.png`, 각 큰 글씨 대표 화면. README에 상태 도달 방법·데이터·기기·테스트 종류를 남긴다. 사용자의 채팅에서 로컬 이미지가 표시되지 않았으므로 **절대 폴더 경로와 파일명도 함께 제공**한다.

PR 설명은 사용자에게 달라진 행동, 저장 계약 유지, 실제 검증 결과, 남은 출시 조건 순서로 작성한다. 계획 검토를 제품 QA 통과나 출시 승인으로 표현하지 않는다.

## 후속 순서

이번 편집 안전 UX → 목표 설정과 목표 이력 연결 → 검색·즐겨찾기 등 기존 무료 기능의 새 저장소 연결 → 히스토리·설정·최종 내비게이션 → 기존 사용자 실데이터·실기기·플랫폼 베타 검증 순서로 진행한다. 인라인 입력 안내와 검증된 문의 연결도 출시 전 backlog로 남긴다. Android는 같은 상태 계약을 참고하되 이번에 공통 UI 기술이나 동시 출시 일정을 확정하지 않는다. AI 체험·구독은 별도 사용성·비용 검증 단계이며 기존 무료 기록/즐겨찾기를 이번에 제한하지 않는다.

## 다음 구현 에이전트 인계문

이 문서의 Phase 1B만 구현한다. 최신 main과 사용자 작업 상태를 확인한 뒤, 두 편집 시트의 닫기·삭제 확인과 미확정 안내, UIKit 복구 문구를 순서대로 작업한다. 새 UI를 기본 활성화하거나 저장 schema·commit·migration 판정·ID 수명을 변경하지 않는다. 신규 record ID는 편집 세션 동안 고정하고 operation ID는 저장 시도마다 생성하는 기존 계약을 유지한다.

검증 표의 각 항목에 fixture 준비, 실행 명령, 기대값, 실제값, 캡처 경로와 미검증 사유를 남긴다. afterReplace 성공 증거로 미반영·읽기 실패 검증을 대신하지 않는다. 구현 후 기획·디자인은 상태별 동작과 문구를 확인하고, 구현 작성자와 분리한 QA 검증을 요청한다. 이번 공동 계획 검토는 실행 QA 통과가 아니다. PR·머지·출시 등 후속 실행 범위는 구현을 맡기는 사용자의 지시를 따른다. 이번 요청에서는 문서만 작성한다.
